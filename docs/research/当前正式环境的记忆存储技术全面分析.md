## 二、各层技术详细分析

### 2.1 Hindsight RAG（L5 长期记忆）

#### 技术栈

| 组件 | 技术选型 | 版本/规格 |
|------|---------|----------|
| **数据库** | PostgreSQL 15 | shared-postgres 容器，端口 5434 |
| **向量扩展** | pgvector | 1024 维 |
| **Embedding 模型** | BAAI/bge-m3 | SiliconFlow API，8192 tokens 上下文 |
| **Reranker** | BAAI/bge-reranker-v2-m3 | SiliconFlow API，cross-encoder |
| **检索引擎** | Hindsight daemon | 端口 9177，HTTP API |
| **LLM** | s-deepseek-v4-flash | LiteLLM 网关 4142 |

#### 数据规模（2026-05-30 验证）

| 表 | 记录数 | 说明 |
|----|--------|------|
| `memory_units` | 24,865 条 | 核心记忆单元 |
| `chunks` | 4,787 条 | 向量化块（远少于 memory_units） |
| `entities` | 7,876 个 | 提取的实体节点 |
| `unit_entities` | 59,011 条 | 记忆-实体关联 |
| `memory_links` | 1,140,081 条 | 记忆间关联关系 |
| 其中 causal | ~5,085 条 | 因果链（0.44%） |

#### 检索管线（7 阶段）

| Phase | 名称 | 说明 | 耗时 |
|-------|------|------|------|
| 1 | generate_query_embedding | bge-m3 生成查询向量 | ~0.5s |
| 2 | parallel_retrieval[9] | 9 路并行检索（semantic×3 + keyword×3 + 其他） | ~1s |
| 3 | rrf_merged[1,563] | Reciprocal Rank Fusion 融合 | ~0.1s |
| 4 | reranked[300] | Cross-encoder 精排 | ~0.5s |
| 5 | entry_points[10] | 选 10 个入口节点 | ~0.01s |
| 6 | visits[300] | 图遍历展开 | ~0.1s |
| 7 | pruned[0] | 裁剪冗余 | ~0.01s |

**总耗时**: ~2-3 秒

#### 检索能力评估

| 能力 | 状态 | 说明 |
|------|------|------|
| 语义搜索 | ✅ 成熟 | 9 路并行 + RRF 融合 + cross-encoder |
| BM25 关键词 | ✅ 成熟 | 与语义搜索互补 |
| 实体图遍历 | ✅ 成熟 | 7,876 实体 + 59,011 关联 |
| 因果链检索 | ⚠️ 数据不足 | 仅 0.44%，但 Hindsight 已内置 link_expansion 加权重排 |
| 时间过滤 | ✅ 可用 | `query_timestamp` 参数 |
| 多类型检索 | ✅ 可用 | world/experience/observation 类型过滤 |

#### 局限性

| 局限 | 影响 | 缓解方案 |
|------|------|---------|
| **无内置遗忘机制** | 记忆只增不减，无 TTL/prune | 外部脚本定期清理 |
| **access_count 始终为 0** | 无法按使用频率做淘汰 | 不可用 |
| **tags 始终为空** | 无法按标签做筛选 | 不可用 |
| **chunks 远少于 memory_units** | ~80% 记忆无向量化块 | 召回率受影响 |
| **因果链数据不足** | 99.5% 是盲关联 | Phase 1 补齐 + 文本富化 |
| **因果链 fact_type 限制** | 跨类型因果链被 SQL 过滤 | 写入时确保同类型 |

### 2.2 Axiom Wiki（结构化知识库）

#### 技术栈

| 组件 | 技术选型 | 规格 |
|------|---------|------|
| **搜索引擎** | Orama | 向量数据库 |
| **Embedding 模型** | Qwen/Qwen3-Embedding-8B | SiliconFlow API，4096 维 |
| **LLM 生成** | DeepSeek v4 | /v1/chat/completions（需 patch 修复 /v1/responses 兼容） |
| **MCP 桥接** | axiom-wiki-mcp.sh | SSE transport，端口 4143 |
| **UI** | Obsidian | 用户通过 Obsidian 查看，非 Axiom 自带 UI |

#### 数据规模

| 指标 | 数值 |
|------|------|
| 页面数 | 38+ |
| 分类 | AI建设、代码编程、工作日志、系统配置、analyses 等 |
| 索引文件 | wiki/search.index |

#### 检索能力评估

| 能力 | 状态 | 说明 |
|------|------|------|
| 语义搜索 | ✅ 可用 | Orama 向量搜索 |
| 全文检索 | ✅ 可用 | 与语义搜索结合 |
| 图导航 | ⚠️ 有缺陷 | map-state.json 可能缺失（DeepSeek 兼容性问题） |
| 分类浏览 | ✅ 可用 | 通过 Obsidian 文件树 |

#### 与 Hindsight 的关系

| 维度 | Hindsight | Axiom Wiki |
|------|----------|-----------|
| **用途** | Agent 内部记忆（RAG） | 用户结构化知识库 |
| **检索方式** | 语义 + BM25 + 图遍历 | 语义搜索 |
| **数据格式** | 结构化表（memory_units 等） | Markdown 页面 |
| **更新方式** | hindsight_retain API | MCP write_page |

| **嵌入模型** | bge-m3 (1024 维) | Qwen3-Embedding-8B (4096 维) |

**关键设计决策**: 两者互补不替代。Hindsight 覆盖 Agent 运行时记忆，Wiki 覆盖用户可读的结构化知识。

### 2.3 MEMORY.md / USER.md（L3/L4 高频记忆）

#### 技术栈

| 组件 | 技术选型 | 规格 |
|------|---------|------|
| **格式** | 纯文本平铺 | §分隔，无元数据 |
| **容量** | MEMORY.md=50K, USER.md=10K | 字符限制 |
| **注入方式** | 冻结快照 | 每轮对话开始时读取，会话期间不变 |

#### 数据特征

| 特征 | 说明 |
|------|------|
| **无时间戳** | 无法判断条目写入时间 |
| **无属性关联** | 无法判断两条记录的关联 |
| **无结构分区** | 纯平铺，无分类/索引 |
| **有次序** | 写入顺序隐含时间轴 |
| **当前占用** | MEMORY.md ~12% (5,929/50,000), USER.md ~26% (2,557/10,000) |

#### 检索能力评估

| 能力 | 状态 | 说明 |
|------|------|------|
| 全文搜索 | ✅ 可用 | 直接文本匹配 |
| 语义搜索 | ❌ 不可用 | 无 embedding |
| 结构化查询 | ❌ 不可用 | 无元数据 |
| 增量更新 | ✅ 可用 | append/replace/remove |

#### 局限性

| 局限 | 影响 | 缓解方案 |
|------|------|---------|
| 容量有限 | 高频内容挤占空间 | 定期清理 + 迁移到 Hindsight |
| 无时间戳 | 无法判断新旧 | 靠写入顺序推断 |
| 无结构 | 难以分类检索 | 靠 LLM 语义理解 |
| 无关联 | 条目孤立 | 靠内容重叠推断关联 |

| RRF 融合惩罚 | 单路因果链 RRF score=0.00114 | 比多路低 30 倍 |
| 文本富化效果 | RRF score 提升 13.7x | 因果链从不可见到可见 |

## 四、关键问题诊断

### 4.1 Hindsight 数据质量问题

| 问题 | 数据 | 根因 | 影响 |
|------|------|------|------|
| chunks 远少于 memory_units | 4,787 vs 24,865 | ~80% 记忆无向量化块 | 召回率受损 |
| causal 链占比低 | 0.44% | 自动提取能力有限 | 因果推理弱 |
| access_count=0 | 全部为 0 | Hindsight 不追踪使用频率 | 无法做热度淘汰 |

| 问题 | 根因 | 影响 | 修复 |
|------|------|------|------|

| 维度不匹配 | Orama 默认 768 维 | 索引失效 | config.json 设 dimensions=4096 |

### 4.3 MEMORY.md 维护问题

## 七、总结

### 7.1 整体评估

| 层级 | 成熟度 | 主要优势 | 主要短板 |
|------|--------|---------|---------|
| L0 上下文 | ✅ 成熟 | 模型能力强 | 容量有限 |
| L2 Session DB | ✅ 成熟 | 毫秒级检索 | 仅关键词 |
| L3 MEMORY.md | ✅ 成熟 | 注入快，高频 | 容量有限，无结构 |
| L4 USER.md | ✅ 成熟 | 用户偏好集中 | 容量有限 |
| L5 Hindsight | ⚠️ 半成熟 | 检索能力强，数据规模大 | 无遗忘机制，chunks 不足 |
| Wiki | ⚠️ 半成熟 | 结构化，用户可读 | 兼容性问题，与 Hindsight 独立 |

### 7.2 核心结论

1. **Hindsight 是当前核心记忆系统**，检索管线成熟（语义+BM25+ 实体图+ 因果链），但数据质量需提升（chunks 不足、因果链少）
2. **Axiom Wiki 与 Hindsight 互补**，前者用户可读，后者 Agent 内部使用，两者独立不替代
3. **MEMORY.md 是高频缓存**，需定期清理迁移到 Hindsight
4. **知识导航系统有效**，因果链补齐 + 文本富化显著提升召回率
5. **最大改进空间**：Hindsight 数据质量（chunks 补齐、因果链自动化）、记忆生命周期管理
