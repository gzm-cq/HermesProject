## 一、知识点定义

知识点 = 一条客观的、不可再分的知识单元，属于下面五类之一。

### 1. 原理

**定义**: 描述"X 通过/因为/遵循 Y → Z"的机制性关系。

**判断标志**: 句子中包含因果/推导/机制类动词（因为、所以、通过、使、遵循、基于、依赖于）。

**用途**: 用于因果推理。知道原理后，你能推导出"如果 X 变了，Z 会怎么变"。

**合法格式**: 

| 例句 | 满足条件 | 
|:---|:---|
| "Q/K 分离使 query 不进 K 空间" | ✅ 有因果（"使"），有结果（query 不进 K 空间），可推理 |
| "HDBSCAN 通过层次聚类覆盖不同密度的簇" | ✅ 有机制（"通过"），有结果（覆盖不同密度） |

**驳回案例**:

| 文本 | 驳回原因 |
|:---|:---|
| "注意力机制由 Q/K/V 三个向量组成" | 这是"是什么"，不是"为什么/如何"，应归为要点 |
| "系统性能和准确率需要平衡" | 没有机制描述，没有因果方向 |
| "1+1=2" | 是公式，不是原理（没有机制说明） |

---

### 2. 公式

**定义**: 可复现、可引用的形式化表述，含操作(变量)→输出的关系。

**判断标志**: 包含数学符号、等号、算子名（softmax、cosine_similarity、Σ、√）、参数变量。

**用途**: 用于计算。知道变量值就能算出结果。

**合法格式**:

| 例句 | 满足条件 |
|:---|:---|
| "attention = softmax(Q × K^T / √d)" | ✅ 有输入变量、有操作、有输出 |
| "余弦相似度 = dot(A, B) / (|A| × |B|)" | ✅ 有输入、有操作、可计算 |
| "指数移动平均：new = α × emb + (1-α) × old" | ✅ 有变量 α、emb、old，可代入 |

**驳回案例**:

| 文本 | 驳回原因 |
|:---|:---|
| "1+1=2" | 纯常量，无变量，无法代入计算 |
| "准确率 = 正确数 / 总数" | 太泛化，等同于定义，无使用价值 |
| "使用以下公式计算相似度" | 元信息（指向公式但不是公式本身） |

---

### 3. 要点

**定义**: 陈述"X 是什么/有什么/怎么分/怎么做"的事实。

**判断标志**: 断言存在或属性，不解释为什么。包含分类、结构、方法步骤、属性描述。句子中通常没有因果动词。

**用途**: 用于理解结构。知道某个东西由什么构成、怎么分类、遵循什么方法。

**合法格式**:

| 例句 | 满足条件 |
|:---|:---|
| "自进化Agent 分为三大范式：模型中心、环境中心、模型-环境共进化" | ✅ 分类关系，列举了各类 |
| "Memory consolidation 包含 embedding 重算和簇中心更新两个步骤" | ✅ 结构描述，说明了组成 |
| "三层管线分为：分析、拆解、准入" | ✅ 结构描述，各阶段列举 |

**驳回案例**:

| 文本 | 驳回原因 |
|:---|:---|
| "自进化Agent 分为三大范式"（不说哪三大） | 只说"有分类"不说分类是什么，无使用价值 |
| "系统包含多个模块" | 太泛化，没有具体模块名 |
| "本文介绍了三种方法" | 元信息，不是方法本身 |

---

### 4. 结论

**定义**: 在特定条件下，X [比较词] Y 或 X 经过验证的属性。

**判断标志**: 包含比较级、优劣判断、经验结果（优于、高于、比...更、有效性、提升、验证、发现）。**必须包含条件或上下文**。

**用途**: 用于决策。知道在什么条件下什么更好。

**合法格式**:

| 例句 | 满足条件 |
|:---|:---|
| "HDBSCAN 在非均匀密度数据上优于 DBSCAN" | ✅ 有条件（非均匀密度数据），有对比（优于） |
| "将 MIN_SCORE 从 0.7 调整到 0.6 后，注入率从 32% 提升至 60.4%" | ✅ 有条件（阈值调整），有结果（提升） |
| "pre_llm_call 实现 100% 确定性触发，替代概率性 SOUL 协议" | ✅ 有条件（pre_llm_call），有对比结果（确定性替代概率性） |

**驳回案例**:

| 文本 | 驳回原因 |
|:---|:---|
| "性能更好" | 没有条件（什么比什么？在什么场景？） |
| "准确率达到了最高" | 没有基准（比谁最高？） |
| "在我们的实验中发现效果很好" | 条件不具体（"效果很好"不可验证） |

---

### 5. 方法/流程

**定义**: 描述可复现的操作步骤、标准流程、方法学、规范。

**判断标志**: 包含步骤序列（首先/其次/最后、Step1/2/3）、秩序动词（执行、运行、配置、部署、导入）、规范性表达（应该、必须、需要、建议）。

**用途**: 用于执行。知道在某个场景下该怎么做。

**合法格式**:

| 例句 | 满足条件 |
|:---|:---|
| "部署流程分三步：备份 → 同步 → 验证" | ✅ 有步骤序列，可复现执行 |
| "Memory consolidation 应在系统空闲时触发，避免影响在线推理" | ✅ 有执行建议，有上下文（空闲时） |
| "导入新知识前必须先运行准入过滤，确保符合五类定义" | ✅ 有规范性要求（必须先） |

**与「要点」的边界规则**：当一条文本同时符合「方法/流程」和「要点」的定义（如"部署流程分三步"既是一个事实，也是一套步骤），**优先归入方法/流程**。理由：方法/流程对执行有直接指导价值，归入后可被纠错回路降级为要点，但反之不能自动升级。

**驳回案例**:

| 文本 | 驳回原因 |
|:---|:---|
| "Step 1：打开文件" | 操作粒度太细，不具有知识价值 |
| "按需调整参数" | 没有具体步骤，无法复现 |
| "具体流程因项目而异" | 没有可复用的内容 |

## 二、原子性与 claims_count

### 定义

一条知识点如果包含两个**独立可验证的 claim**（事实性断言），则不是原子的。

独立可验证的含义：
- Claim A 成立与否不依赖 Claim B 的上下文
- 去掉 Claim B 后，Claim A 仍然是一句完整的有知识价值的话

### 判断方法：拆分测试

把一句话拆成两句，如果两句都独立成立，则不是原子。

**非原子：**
```
"自进化Agent分为三大范式，其中模型中心通过离线推理自我改进"
```
拆分：
- "自进化Agent分为三大范式" → 独立成立 ✅
- "模型中心通过离线推理自我改进" → 独立成立 ✅
→ 应拆为两条

**原子（列举分类）：**
```
"自进化Agent分为三大范式：模型中心、环境中心、模型-环境共进化"
```
- "自进化Agent分为三大范式" → 独立成立
- "三大范式：模型中心、环境中心" → 脱离上下文不成立
→ 是原子（列举的名词是实例化，不是新 claim）

### claims_count

每条知识附带一个 `claims_count`，表示包含的独立事实断言数。
- `claims_count > 1` 则非原子，需继续拆解
- `claims_count == 1` 则为原子

### claims_count 的可靠判定

由于 LLM 对同一句话的 claims_count 输出可能波动，采用混合判定（规则兜底 + 结构化输出 + 拆解后校验）。

**1. 规则级硬边界修正（零 LLM 成本）**

在阶段1 LLM 产出 claims_count 后，通过以下规则修正：

- 文本包含「且、并、同时、分别、一方面…另一方面、但是、然而」等连词 → `claims_count = max(claims_count, 2)`
- 文本包含「；」或「;」→ `claims_count = max(claims_count, 分号数 + 1)`
- 文本包含两个独立主谓结构（多逗号长句）→ `claims_count = max(claims_count, 2)`

修正规则**只向上调整**（不降低 LLM 输出的值），避免低估。

**2. 结构化输出要求**

阶段1 的 LLM 调用必须输出显式的 claim 列表，而非仅一个数字：

```text
文本：模型中心通过离线推理自我改进，环境中心通过增强交互实现进化
输出：
claim: 模型中心通过离线推理自我改进
claim: 环境中心通过增强交互实现进化
claims_count: 2
```

这样 claims_count 可审计——人工可检查 claim list 是否正确，而非只看一个数字。

**3. 阶段2 拆解后的 sum 校验**

拆解后，所有子条目的 claims_count 之和应等于原 claims_count：

- `sum(sub_claims) == 原值` → 校验通过
- `sum(sub_claims) != 原值` → 标记一致性警告，触发**重新分析**（1 次机会）
  - 仍校验不通过 → 用规则修正值覆盖 LLM claims_count（规则值至少确保显式连词/分号场景不低估）；规则值也为 0 → 写入 review_queue（类型 `consistency_warning`），不丢弃（见 12.5 审查队列）

## 三、管线概述与迁移策略

> **迁移策略**：直接**全量重建**——旧树只跑过一次且效果不好，没有保留价值。
> 清理旧树 → 用新管线重跑所有已入库文章的源文件。
> 重建前确认源文件目录可访问。
>
> **注意**：重建后所有知识 ID 会变更，纠错回路积累的数据（confidence 分数、点击日志、review_queue 条目）将因 ID 变更而失效。当前数据量小，允许丢失；后续重建前需评估是否迁移纠错数据。

```
文件系统
  │
  ▼
[Pre-phase: 输入扫描]
  │  扫描输入目录，排除非知识文件
  │  递归子目录，产出入列文件列表
  │  产物：admitted_files.json
  │
  ▼
[阶段1: 分析]
  │  扫全文，找匹配五类定义的内容
  │  不预判值不值得分析；阶段1 本身不限条数，但成本控制层在超过 K=15 时截断（见九、成本控制）
  │  附带文章类型标记
  │  产物：analysis_report.json
  │
  ▼
[阶段2: 拆解]
  │  规则级 claims_count 修正（连词/分号检测）
  │  检查每条候选的 claims_count
  │  claims_count > 1 → 拆到 == 1（上限 2 轮），拆后 sum 校验
  │  验证自解释性（三项具体规则）
  │  产物：atomic_knowledge_list.json
  │
  ▼
[阶段3: 准入 + 去重]
  │  规则兜底拦截
  │  两段式去重（embedding + LLM 确认）
  │  产物：admitted_knowledge_list.json
  │
  ▼
[阶段4: 树定位]
  │  将知识点归入知识树：领域→科目
  │  关联父科目，生成入树记录
  │  产物：tree_insertion_records.json → 入库
```

### Pre-phase：输入扫描

**职责**: 从文件系统中选取可分析的文件，排除不适合建树的文件。

**流程**：
1. 扫描输入目录（递归子目录）
2. 排除非知识文件：`index.md`、`moc.md`、`_bak/`、`_archive/`、日志文件、模板文件
3. 过滤空文件、二进制文件（图片/PDF 解码失败的原始文件）
4. 输出 `admitted_files.json`（[filepath, title] 列表）

**失败处理**：
- 输入目录不存在或为空 → 输出 `{ empty_dir: true, admitted_files: [] }`，管线终止
- 单个文件读取失败（编码问题/权限）→ 跳过该文件，继续处理剩余，记录错误日志

**不做的事**：
- 不做内容理解（那是阶段1的事）
- 不做数量限制（有多少合规文件就入列多少）

**产出格式**：
```json
{
  "source_dir": "pages/analyses/",
  "admitted_files": [
    {"path": "pages/analyses/evaluation/llm-as-judge.md", "title": "LLM-as-Judge 评估方法综述"},
    {"path": "pages/analyses/self-evolution/dspy-comparison.md", "title": "DSPy vs 自主Agent 框架对比"}
  ],
  "skipped": [
    {"path": "pages/analyses/index.md", "reason": "目录索引页"},
    {"path": "bak/old-design.md", "reason": "备份目录"}
  ],
  "empty_dir": false
}
```

### 阶段1：分析

**职责**: 通读全文，找到所有和五类定义匹配的内容，并预判文章来源类型（辅助后续阶段判断）。

**不做的事**：
- 不预判"值不值得分析"（看过才知道，不跳过任何文件）
- 不限数量（不说"提取3-8条"）
- 不做最终准入判断（那是阶段3的事）
- **不做文章类型预判**（`article_type` 已移除——领域匹配由阶段4 关键词规则表处理，不需要阶段1 预判文章类型）

**逻辑**：
逐段扫，对每一段问：这段里有符合原理/公式/要点/结论/方法/流程的东西吗？
有就列出，顺便标类型、估 claims_count。
没有就跳过。
全文扫完，输出 report。

特别地，每一条候选必须满足**合法格式**要求（见第一章各类型的"驳回案例"）：
- 原理必须有因果/机制方向，不能只说"是什么"
- 公式必须有变量，不能是纯常量
- 要点必须有具体内容，不能只说"有分类"不说什么分类
- 结论必须有条件基准，不能只说"更好"不说在什么条件下

**产出格式**（`article_type` 已被移除——领域匹配走关键词规则表，不需要文章类型标记；如需降级到 LLM 判断领域，由阶段4 自行调用，不由阶段1 预判）：
```json
{
  "article_title": "自进化智能体领域全景图",
  "analysis": {
    "content_summary": "文章对自进化Agent领域做了全景梳理，介绍了三大范式和技术演进路径",
    "empty_article": false
  },
  "candidates": [
    {
      "text": "自进化Agent分为三大范式：模型中心、环境中心、模型-环境共进化",
      "type": "key_point",
      "claims_count": 1
    },
    {
      "text": "模型中心通过离线推理自我改进，环境中心通过增强交互实现进化",
      "type": "principle",
      "claims_count": 2
    }
  ]
}
```

### 阶段2：质量评估 + 拆解

**职责**: 评估每一条候选是否为合格的知识点。不合格的拆解到合格，不可拆的丢弃。\
对合入知识点做类型验证，识别是否需要修正。

**输入**: 阶段1的 analysis_report.json（candidates 列表）  
**输出**: 通过评估的原子知识列表

**流程**:

对每条 candidate，先做**原子性检查**：
- `claims_count == 1` → 走**质量评估**
- `claims_count > 1` → 先走**规则级修正**（连词/分号检测），再走**拆解**（LLM 拆成多条，上限 2 轮），拆完后做 **sum 校验**（子 claims_count 之和 == 原值），通过则回到原子性检查
- 2 轮后仍有 `claims_count > 1` → **保留已拆出的合格子条目**，残余写入 review_queue（类型 `incomplete_split`，7 天超时自动丢弃），不立即丢弃——残余可能本身有价值，只是 LLM 未拆好，等纠错回路介入

```
输入 → [规则级 claims_count 修正]
         ↓
      [原子性检查]
  ├─ 已原子 → [质量评估]
  │             ├─ 格式合法？(公式有变量？结论有条件？)
  │             ├─ 类型匹配？(类型与文本一致？)
  │             ├─ 自解释？（三项具体规则，见下文）
  │             ├─ 全部通过 → 阶段3
  │             └─ 不通过 → 丢弃
  ├─ 非原子 → [LLM拆解] (上限2轮)
  │              ├─ 拆完 + sum 校验通过 → 回到原子性检查
  │              └─ 2轮未完全拆完 →
  │                  保留已拆合格部分，残余入 review_queue
  └─ 两类外 → 丢弃
```

**质量评估的三项检查**：
1. **原子性** — `claims_count == 1`
2. **格式合法** — 各类型的合法格式要求（公式有变量、结论有条件、原理有因果方向、要点有具体内容）
3. **类型匹配** — 阶段1标记的类型是否符合文本实际（如"原理"类文本实际是"要点"，修正类型后继续）
4. **自解释** — 知识点文本在脱离原文后仍可独立理解。
   **三项具体规则**（任一违反即拒绝）：
   - 不能包含指代前文的代词：如「该模型」「这种方法」「上述算法」
   - 不能包含元引用：如「如上所述」「下文详述」「前文提到」
   - 不能包含依赖原文才能理解的省略或文章自创缩写：如「将其分为三类」但不说明哪三类、或文章中自定义的缩写如 SE-Agent-Arch（非域内通用）

   **缩写宽容原则**：域内通用缩写（HDBSCAN、DBSCAN、RAG、LLM、PG、SQL、API、CLI、JSON、YAML、embedding、token 等）不需要展开。判断标准是「该领域一个合格从业者是否不需要查资料就能理解」。不确定时优先保留（宁过勿拒），让纠错回路过滤。

   ✅ 接受例：「HDBSCAN 通过层次聚类覆盖不同密度的簇」— HDBSCAN 是域内通用，语义完整
   ❌ 拒绝例：「该方法通过上述机制实现」— 指代不明
   ✅ 接受例：「RAG 通过外部知识库增强 LLM 的生成质量」— RAG 和 LLM 均为域内通用

**拆解的约束**：
- 不需要原文上下文——候选文本本身应该承载完整语义
- 拆完后每条独立走质量评估，不合格的直接丢弃
- 拆解后做 **sum 校验**：子条目 claims_count 之和 == 原 claims_count
- 不一致的处理链路：
  1. 触发**重新分析**（与阶段1 同一 LLM 调用，1 次机会）
  2. 二次校验仍不一致 → 用**规则修正值**覆盖 LLM claims_count（见二 §claims_count 可靠判定中的规则级硬边界。规则值至少确保显式连词/分号场景不低估）
  3. 规则值也为 0 或仍不合理 → 标记为 `consistency_warning`，写入 review_queue
- 不修复、不补全、不猜测——阶段1的产物不完善就拆，拆不了就保留已拆部分

### 阶段3：准入 + 去重

**职责**: 规则兜底拦截 + 跨文章两段式去重 + 矛盾检测。

**输入**: 通过阶段2的原子知识列表  
**输出**: 最终入树的知识列表

**流程**：

```
原子知识列表 → [兜底拦截] → [去重] → [矛盾检测] → 入树列表
```

**兜底拦截规则**（纯规则，零 LLM 调用）：

| 规则 | 例子 | 
|:---|:---|
| 类型不在五类中 | "操作指南"、"任务状态" 等 |
| `claims_count > 1`（阶段2遗漏） | — |
| 长度 < 10 字 | "性能更好" |
| 提取失败信号 | 包含"无法提取"、"已被删除"、"无法读取"、"请提供" |
| 元信息开头 | 以"本文介绍了"、"本文讨论了"、"本文分析了"、"文章概述了"、"综述总结了" 开头 |

**去重逻辑**（两段式）：

两篇不同文章可能产出了相同的知识点。去重分两段：

1. **第一段（embedding 初筛，零 LLM）**：计算新知识点与库中知识的 cosine similarity。\
   - `> 0.95` → 直接判重，跳过
   - `0.90 ~ 0.95` → 进入第二段（阈值见成本控制章节）
   - `< 0.90` → 不重复，通过

2. **第二段（LLM 确认）**：对新知识点与高相似但未达直接判重阈值的老知识做语义等价判断。
   采用**批量判断**，每批 5 对候选，减小调用次数。\
   - 语义等价 → 判重跳过
   - 语义不等价 → 保留

阈值可调（经验值，上线后根据误判率修正）。

**阈值校准方法**：
- 上线前从知识库随机采样 200 对知识点，人工标注「是否重复」
- 对标注集画 precision-recall 曲线，选 f1 最优的阈值。同时确认 0.90 作为 LLM 确认下界是否合理——如果 PR 曲线显示 0.85 处 recall 显著优于 0.90 而 precision 损失可接受，则放宽至 0.85
- 不同 embedding 模型需分别校准（bge-m3 的相似度分布与 text-embedding-ada-002 不同）
- 上线后每季度复校一次，或在 review_queue 中的去重误判数 > 50 时触发重校

**矛盾检测**：

在去重之后，检查新知识点与同领域现有知识点是否存在语义矛盾。

判定分为两步：

1. **条件是否相同**：比较新知识与现有知识点的条件描述（如「在非均匀密度数据上」「temperature=0.8时」）。通过关键词重叠判断：如果条件部分的词语重叠度 < 0.3（如「非均匀密度」vs「高维稀疏」），视为条件不同 → **不判定矛盾**，保留双方。
2. **结论是否对立**：仅当条件判定为相同后，检查结论方向是否相反。一条包含否定关键词（不、不是、不能、无效、相反、错误），另一条不包含 → 判定为矛盾。

示例：
- "HDBSCAN 在非均匀密度数据上优于 DBSCAN" vs "DBSCAN 在高维稀疏数据上优于 HDBSCAN" → 条件不同 → 不矛盾 ✅
- "HDBSCAN 在非均匀密度数据上优于 DBSCAN" vs "DBSCAN 在非均匀密度数据上优于 HDBSCAN" → 条件相同 + 结论对立 → 矛盾 ⚠️

**去重与矛盾的防重叠规则**：已判定为矛盾（进入 review_queue）的知识对，不再进入去重 LLM 检查——已被确认为不同知识而非重复。反过来，被去重 LLM 判为"不等价"的知识对，仍进入矛盾检测。顺序保证：去重先于矛盾。

满足矛盾条件时写入 `review_queue`（见 12.5 审查队列），不阻断入库。
```json
{
  "type": "contradiction",
  "new_text": "DBSCAN 在非均匀密度数据上优于 HDBSCAN",
  "existing_id": 42,
  "existing_text": "HDBSCAN 在非均匀密度数据上优于 DBSCAN",
  "similarity": 0.85,
  "condition_same": true,
  "status": "pending_review"
}
```
保留双方，等待 12.4 的纠错回路解决。

**冷启动处理**：
- 首次运行时知识库为空，去重阶段 trivially 全部通过
- 首批文章建议一次性灌入 ≥ 5 篇，让知识库快速积累到可去重的基数
- 基数 < 50 条时，去重退化为纯文本匹配（精确字符串匹配）
- **注意**：阶段3（去重）和阶段4（科目匹配）的冷启动阈值不同（50 条 vs 3 篇），两者可能不同步。例如 2 篇长文可产出 60 条 → 阶段3 warm 但阶段4 cold。不是错误行为，无需对齐。实现时注意两个阶段独立判断冷/热状态。

**失败处理**：
- 阶段2输出为空 → 阶段3 直接跳过，无知识点入树
- 去重阶段 LLM 调用超时 → 回退到仅 embedding 去重（0.90 阈值直接判重），标记该批次为「降级」
- 全部失败 → 输出空列表而非中断管线

**不做的事**：
- 不做质量判断（阶段2已完成）
- 不做内容理解（不调用 LLM）
- 不做分类修正（类型在阶段1定、阶段2验证）
- 不做同义表述（aliases）提取——暂时不需要，后续再考虑

### 阶段4：树定位

**职责**: 将已准入的知识点归入知识树的正确层级（领域→科目→知识点），建立父子关系。

**输入**: 阶段3的 admitted_knowledge_list.json  
**输出**: tree_insertion_records.json（含树路径、父科目 ID、置信度）

**流程**：

```
admitted_knowledge_list.json → [领域匹配] → [科目匹配] → [生成插入记录] → 入库
```

1. **领域匹配** — 规则表为主，LLM 兜底。\
   \
   **优先走规则表**：维护一个 50 条以内的 keywords → domain 映射表。\
   初始示例只覆盖了 4 个领域（clustering/attention/rag/benchmark），上线前需根据源文章的实际分布补充到至少 20 条规则，特别是项目相关的 self-evolution 领域（Reflexion/Voyager/ExpeL/Agent Lightning 等四代技术路线）。\
   ```yaml\
   # domain_rules.yaml（示例）\
   rules:\
     - keywords: [聚类, HDBSCAN, DBSCAN, 簇]
       domain: mlops/clustering\
     - keywords: [attention, transformer, 注意力, Q/K, 自注意力]
       domain: deep-learning/attention\
     - keywords: [RAG, 记忆, memory, 召回, 检索]
       domain: memory-system/rag\
     - keywords: [评估, benchmark, 对比, 指标, 准确率]
       domain: evaluation/benchmark\
   ```\
   匹配方式：文章标题 + content_summary 中的关键词命中最长匹配规则。\
   零 LLM 成本，结果确定。\
   \
   **未匹配时降级到 LLM**：传入文章标题 + content_summary，要求从已有领域列表中选择。\
   prompt 限制输出格式为领域路径字符串。\
   \
   **输入**: 文章标题 + 阶段1产出的 content_summary\
   **输出**: 领域路径字符串（如 `mlops/clustering`）

2. **科目匹配** — 在目标领域下，用语义匹配定位到最合适的已有科目（cosine > 0.7），找不到则创建新科目。\
   科目创建规则：同一文章产出知识点中 > 3 条无法匹配已有科目 → 创建新科目并以领域内特有概念命名。

   **冷启动处理**：
   - 知识树为空时，首批文章按领域直接创建根科目（如 `evaluation/`、`memory-system/`）
   - 首篇文章的每条知识点自动创建为科目下的叶子节点
   - 首批 ≥ 3 篇后科目匹配功能才生效

3. **生成插入记录** — 每条知识点的入树记录：
   ```json
   {
     "knowledge_text": "HDBSCAN 在非均匀密度数据上优于 DBSCAN",
     "type": "conclusion",
     "domain": "mlops/clustering",
     "subject": "DBSCAN vs HDBSCAN",
     "parent_knowledge_id": null,
     "quality_confidence": 0.85,   // 初始质量信心，区别于 12.3 的动态检索 confidence
     "source_article": "self-evolution/clustering-comparison.md",
     "k_vector": null
   }
   ```

**边界情况**：
- 跨领域知识点 → **知识点只存储一份**（唯一 ID），副领域以引用链接关联。查询时从主领域返回，附带跨域标签；同一知识点不被重复检索。
- 无法归入已有树结构的知识点 → 标记为"游离"，写入 review_queue（类型 `orphan`），但不影响入库（见 12.5 审查队列）

**失败处理**：
- 领域匹配失败（无对应映射）→ 标记为 `domain: unknown`，知识点仍入树但归入「未分类」根节点
- 科目匹配全部失败（所有知识点 cosine < 0.7 且不符合创建条件）→ 统一归入领域下的「其他」科目
- 单条知识点插入失败 → 跳过该条，继续处理剩余，最终报告失败数

**不做的事**：
- 不做知识质量再评估（阶段2已完成）
- 不做全树重建（只增量入库）

## 九、LLM 成本预算与控制

> 改造方案相对于现有 pipeline，LLM 调用次数增长显著。本节定义成本控制参数和优化策略，上线前需以此为基准做 token 预算。

### 默认参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 每篇候选数上限 K | 15 | 阶段1 返回超过此数时，只保留前 K 条 |
| 拆解轮数上限 R_max | 2 | 2 轮未完全拆完则保留已拆合格部分 |
| LLM 去重触发阈值 θ_dedup_llm | 0.90 | cosine > 0.90 才进 LLM 确认（区间缩窄至 0.90~0.95） |
| 直接判重阈值 θ_dedup_direct | 0.95 | 不变 |
| 去重确认批大小 D_batch | 5 | 每次 LLM 调用处理 5 对候选，减少调用次数 |

### 可选优化：阶段1+阶段2 合并

> ⚠️ **与 claims_count 机制的冲突**：合并后 LLM 直接输出原子列表，不存在独立的 claims_count 中间值。因此规则级硬边界修正、结构化 claim list、sum 校验全部失效。选择合并则**跳过 claims_count 校验**，质量保障退化为端到端 LLM 输出。不合并则保留完整 claims_count 链路，但 LLM 调用量高。上线建议：Phase A 用不合并版本验证 claims_count 效果，稳定后再评估是否切合并。

将「分析 + 拆解 + 质量评估」放入同一次 LLM 调用，由 LLM 在内部完成拆解后直接输出原子列表。

```
合并 prompt 结构:
1. 从文章中提取所有符合五类定义的知识点候选
2. 对每个候选，列出其包含的独立 claim
3. 如果 claim > 1，直接拆成多条
4. 检查每条是否符合原子性 (claims_count == 1)
5. 输出最终原子列表
```

**收益**: 阶段2的拆解 LLM 调用次数归零。单篇 LLM 调用：1 次（原方案 ~10~19 次）。  
**代价**: 单次 prompt 更长（约 5k tokens vs 原 3k），但总 tokens 降约 80%。

### 降级策略

不是所有文章都需要全管线处理。按源质量分档：

| 源质量 | 管线级别 | LLM 预算 |
|--------|---------|----------|
| 人工精读笔记 | 全流程（分析→拆解→准入→树定位） | 正常 |
| 速读/草稿 | 简化流程（仅阶段1分析→embedding-only去重→直入库，跳过拆解） | 1 次/篇 |
| 自动抓取 | 仅阶段1分析，产物标记 low_confidence 入库 | 1 次/篇 |

### 运维监控

每次管线运行输出成本报告：

```json
{
  "article_id": "xxx",
  "llm_calls": { "phase1": 1, "phase2_splits": 4, "phase3_dedup": 3, "total": 8 },
  "tokens_used": 28000,
  "candidates": { "raw": 15, "after_split": 12, "admitted": 9 },
  "cost_estimate_usd": 0.056
}
```

上线后需追踪：平均 LLM 调用数/篇、异常高消耗文章、逐环节成本分布。

## 十、验收指标

> 改造方案需要可测量的验收标准，以回答「比现在好在哪」「值不值」「什么时候算成功」。

### 质量指标（与当前 pipeline 盲比）

| 指标 | 测量方式 | 当前基线（估算） | 改造目标 | 优先级 |
|------|---------|----------------|---------|--------|
| 知识点通过率 | 人工采样 50 条，统计「有价值」比例 | ~60% | ≥ 80% | P0 |
| 原子性准确率 | 人工检查通过的候选是否真的 claims_count==1 | 无此概念 | ≥ 90% | P0 |
| 类型分类准确率 | 人工判断 vs LLM 标记的类型一致性 | 无此概念 | ≥ 85% | P1 |
| 自解释合格率 | 通过的知识点是否满足三项自解释规则 | 无此概念 | ≥ 95% | P1 |
| 无价值抽取率 | 阶段1候选中被阶段2/3丢弃的比例 | ~40% | ≤ 30% | P2 |

**验收方式**: 从新管线输出中抽样 100 条知识点，由人工评审员盲比；与当前 pipeline 同源文章做对比。

### 成本指标

| 指标 | 当前基线 | 目标上限 | 说明 |
|------|---------|---------|------|
| LLM 调用数/篇 | 1 次 | ≤ 3 次（含拆解+去重）| 见成本控制章节 |
| 单篇 tokens 消耗 | ~3k | ≤ 12k（无合并）或 ≤ 6k（合并后） | 含 prompt + completion |
| 每千条知识成本 | — | 上线后记录定基准 | 长期趋势监控 |

**验收方式**: 跑 20 篇覆盖 survey/design/log 的测试集，统计平均值和 P90。

### Pipeline 健康指标

| 指标 | 说明 | 健康值 | 预警值 |
|------|------|-------|-------|
| 去重命中率 | 被识别为重复的候选占比 | 5~20% | > 30%（阈值太松）或 < 1%（阈值太紧） |
| 拆解率 | 需要拆解的候选占比 | 10~30% | > 50%（阶段1粒度太粗） |
| 产率 | 准入数 / 候选数 | 40~70% | < 20%（过滤太严）或 > 90%（过滤太松） |
| 零知识率 | 产出 0 条知识的文章占比 | < 10% | > 20%（阶段1漏提取） |

### 上线分阶段计划

```
Phase A — 离线验证（1 周）
  ├─ 用 20 篇文章的历史数据跑新老管线对比
  ├─ 人工抽样评审质量指标是否达标
  └─ 产出一份对比报告 → 决策是否上线

Phase B — 灰度上线（2 周）
  ├─ 新管线与旧管线并行运行
  ├─ 新树独立入库，不替代旧树
  ├─ 监控成本指标和健康指标
  └─ 决策是否全量切换

Phase C — 全量切换
  ├─ 全量重建（按迁移策略）
  ├─ 旧树归档
  └─ 持续监控纠错回路
```

## 十一、检索模型

> 改造后的知识树是分类树（领域→科目→知识点），分类树不能直接做语义搜索。
> 必须搭配独立的语义索引层。

### k_vector 的角色

每个知识点入库时，用 bge-m3 对其文本做 embedding，结果存入 `k_vector`。

```
k_vector 的计算时机:
  阶段4 写入时: 对知识点文本做 embedding，存入 k_vector
  consolidation 时: 如果有纠错反馈，可微调 k_vector
```

检索时对所有 `k_vector` 做 ANN 搜索，而非遍历树结构。

> **与 Hindsight 的关系（待定）**：知识树的 k_vector ANN 检索与现有 Hindsight 的语义搜索（HNSW + BM25 + 实体图 → RRF → reranker）是两套独立的检索路径。三者选一：① 替换 Hindsight 的 semantic recall 通道；② 作为 RRF 融合中的新一路；③ 独立运行供 Agent 知识查询使用。本设计文档不替代系统级检索架构决策，实施前需在项目层面确定。

### 三通道检索

```
                    ┌─────────── query ───────────┐
                    │                              │
              ┌─────┴─────┐                ┌──────┴──────┐
              ▼           ▼                ▼             ▼
        [语义索引]   [树导航]         [纠错日志]
      k_vector ANN  目录遍历          记录 recalled/clicked
              │           │                │
              └─────┬─────┘                │
                    ▼                      ▼
              结果合并               feedback 流入纠错回路
              返回 top-K
```

| 通道 | 触发条件 | 实现方式 | 用途 |
|------|---------|---------|------|
| **语义索引**（主）| 用户输入关键词/自然语言 | query embedding → k_vector cosine 搜索 → top-K | 默认检索路径 |
| **树导航**（辅）| 用户指定领域/浏览 | 目录遍历「领域→科目→知识点」 | 知识浏览、领域筛选 |
| **纠错日志** | 每次检索 | 记录 recalled_ids、user_clicked_ids、user_feedback | 数据流入纠错回路 |

### 结果合并

- 语义索引结果附带树路径展示（如 `memory-system/Q-K分离`），用户看到领域上下文
- 树导航聚焦领域过滤，返回该领域下的知识点
- 用户模糊搜索时：语义索引为主，树导航做结果聚类展示

### 检索日志 → 纠错回路

每次检索记录一次日志：

```json
{
  "query": "Q/K 分离原理",
  "recalled_ids": [101, 204, 307],
  "user_clicked_ids": [204],
  "user_feedback": null,
  "timestamp": "2026-06-10T14:32:00Z"
}
```

- `recalled` 但未 `clicked` → 隐性降权（纠错回路 5.3）
- `clicked` → 隐性升权
- 用户明确否定 → 触发纠错回路（5.2：置信度降权或树位置移动建议）

### 与自解释规则的闭环

阶段2 的自解释规则保证知识点脱离原文后可独立理解。检索日志反向验证：

- 高召回 + 高点击 → 自解释成功
- 高召回 + 低点击 → 知识点文本有歧义，标记复查
- 低召回 + 用户期望 → 知识点 embedding 不准确，考虑微调 k_vector

## 十二、纠错回路

知识点入库后，使用过程中的数据和反馈反哺树结构。不是一次性管线交付后不管。

### 12.1 使用日志——谁被用到了

consolidation 时记录每条知识的访问情况：被 recall 了多少次、被引用到回答中多少次、飞书搜索中是否被命中。

### 12.2 用户找不到的反馈

当用户明确表示"不是这个"或"没找到我要的"时，触发反馈路径：

1. 用户给出的正确答案 → 作为新知识点入库（走完整管线）
2. 用户的操作过程 → 记入经验区（未来用于路径优化）
3. 原知识点 → 标记"用户反馈：定位不准"，confidence 降权

### 12.3 信心自然收敛

不需要人工打标签。模式是"数据 flywheel"。

**confidence 衰减公式**（以下为初始经验值，上线后根据实际行为调参校准）：

```
每次检索后：
  if user_clicked_ids contains this knowledge:
    confidence = min(1.0, confidence + 0.05)          // 被点击 → 升权 +0.05
  else if this knowledge in recalled_ids:
    confidence = confidence × 0.99^(days_since_last_click)  // 被召回但未被点击 → 日衰减 1%
  else:
    confidence = confidence × 0.997^(days_since_last_recall) // 长期未被召回 → 日衰减 0.3%

用户明确否定：
    confidence = confidence × 0.5                       // 直接砍半
```

> ⚠️ 以上所有系数（+0.05、×0.99、×0.997、×0.5）及阈值均为初始猜测值，未经实地验证。上线 Phase B 灰度期间需收集 2 周数据后校准：目标使 θ_review 的年触发率在 5~15% 之间，过高则调松衰减率，过低则调紧。

**阈值**：

| 阈值 | 值 | 动作 |
|------|----|------|
| `θ_review` | < 0.3 | consolidation 标记「待审查」，停止在语义索引中返回 |
| `θ_demote` | < 0.5 | 在语义索引结果中降权至第 3 页后 |
| `θ_promote` | > 0.95 | 标记为高置信度知识，纠错回路跳过常规检查 |
| `θ_remove` | < 0.1 | 自动标记为「已废弃」，写入 review_queue（类型 `obsolete`），见 12.5 审查队列 |

**累积规则**：同一知识点连续 3 次检索被召回但未被点击 → 触发一次额外衰减（等效于额外 7 天无点击）。

### 12.4 树结构微调

纠错不止降权。当数据显示知识点归错了科目（如 Q/K 分离知识点被人反复在 "attention-mechanism" 科目下搜到而非 "memory-system"），consolidation 自动生成移动建议，人工确认后重定位。

**移动建议触发条件**：
- 同一知识点在科目 A 被检索到次数 > 在科目 B 被点击次数 × 3
- 且累计被检索到 ≥ 10 次

满足条件时 consolidation 输出移动建议记录：

```json
{
  "knowledge_id": 204,
  "from_subject": "attention-mechanism",
  "to_subject": "memory-system",
  "trigger": "10 retrievals in attention-mechanism, 0 clicks",
  "confidence_before": 0.45,
  "status": "pending_review"
}
```

**人工确认机制**：
- 待确认项写入 `review_queue` 表（与 `incremental.py` 共享）
- 通过 CLI `consolidate review` 子命令列出待确认项，逐条接受/拒绝
- 超过 30 天未确认 → 自动执行移动（安全默认：移动比不移动好）
- 被拒绝的移动建议 30 天内不再为同一知识点生成

### 12.5 审查队列（review_queue）

审查队列是跨阶段的统一人工处理通道。以下场景写入 review_queue：

| 触发场景 | 来源阶段 | 队列类型 | 超时默认动作 |
|---------|---------|---------|------------|
| sum 校验失败（子 claims 之和不等于原值）| 阶段2 | `consistency_warning` | 7 天后自动通过，标记低置信度 |
| 拆解 2 轮后仍有残余 | 阶段2 | `incomplete_split` | 7 天后自动丢弃（残余价值低于正常知识） |
| 矛盾检测触发 | 阶段3 | `contradiction` | 保留双方，永久 pending |
| 游离知识点（无法归入已有树）| 阶段4 | `orphan` | 30 天后自动挂到「未分类」根节点 |
| 置信度降至 θ_remove 以下 | 纠错回路 | `obsolete` | 7 天后自动删除 |
| 科目移动建议 | 纠错回路 | `move_suggestion` | 30 天后自动执行移动 |

**CLI 接口**：

```bash
# 列出所有待审查项（含类型、来源、状态）
knowledge-tree-builder review list [--type contradiction|orphan|move_suggestion]

# 逐条操作
knowledge-tree-builder review accept <id>     # 接受（具体动作取决于类型）
knowledge-tree-builder review reject <id>     # 拒绝（标记已处理，不再重复触发）
knowledge-tree-builder review postpone <id>   # 推迟（重新计时分支）

# 一键批量
knowledge-tree-builder review batch-accept --type move_suggestion

CLI 入口为 `knowledge-tree-builder`（注册为 console_scripts 中的 entry point），也可通过 `python -m knowledge_tree_builder.cli` 调用。
```

**状态机**：

```
pending_review → accept    → 执行对应动作（移动/删除/挂载）
               → reject    → 标记已处理，抑制同类型重复触发
               → (timeout) → 执行默认动作
```

pending 状态的知识点在语义索引中正常返回，但附带 `confidence_warning` 标记，调用方（前端/飞书）可选择性展示。

## 十三、扩展性

5 类知识点不是终态，可以扩展或修正：

| 未来可能新增的分类 | 场景 |
|:---|:---|
| 标准/规范 | 行业标准条款 |
| 经验法则 | 实践中验证的规律 |
| 反模式 | 已知错误的做法 |

扩展原则：分类表变化不触及三阶段判定流程（分析 → 拆解 → 准入），只新增或修订阶段3的分类映射即可。
