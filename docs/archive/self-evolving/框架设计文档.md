## 一、框架概述

### 1.1 核心问题

传统 AI Agent 系统存在**单向执行、无反馈闭环**的局限：任务执行后轨迹被丢弃，失败经验无法积累，Agent 能力不会随使用持续进化。

**本框架的目标**：构建一个三层自进化闭环系统，让 Agent 在执行中持续学习、优化、进化。

### 1.2 框架来源

融合三个代表性研究工作：

| 框架 | 机构 | 核心贡献 | 本框架中的定位 |
|------|------|----------|---------------|
| **SEAL** | 西湖大学 + 蚂蚁集团 | Agent-Environment 协同进化 | 第 4 层（调度层）参考 |
| **SE-Agent** | QuantaAlpha | 轨迹级自进化（三大算子） | 第 2 层（工具层）核心 |
| **CoEvolve** | AMAP-ML（高德地图） | Agent-Data 协同进化 | 第 3 层（数据层）参考 |

### 1.3 框架范围

本框架**排除第 1 层（策略进化/RL 微调）**，原因：

- Hermes 架构使用固定 LLM 模型，不涉及参数微调
- 第 1 层需要大规模 LLM 微调基础设施，超出当前能力范围
- 保留为远期扩展方向，不在本文档实施范围内

**实际实施范围：第 2、3、4 层**

## 三、各层详细设计

### 3.1 第 2 层：工具层（Tool Layer）

**核心定位**：三大进化算子 Skill，可直接调用、独立交付、独立验证。

**来源框架**：SE-Agent（轨迹级自进化）

**核心组件**：三大算子

| 算子 | 定位 | 触发条件 | 输入 | 输出 |
|------|------|----------|------|------|
| **Revision** | 失败驱动的策略生成器 | 代码 bug / 执行失败 / 文档错误 | 失败内容 + 上下文 | 修正内容 + 根本原因 + 3 个替代方案 |
| **Recombination** | 跨轨迹知识合成器 | 多 worker 并行结果 / 多方案融合 | 候选内容列表 + 上下文 | 重组内容 + 组件映射 + 协同评分 |
| **Refinement** | 风险感知优化器 | 长链路精简 / 冗余去除 | 候选内容 + 失败模式库 | 精炼内容 + 缩减统计 + 风险评估 |

**执行流程**：

```
单算子模式：
  用户指令 → 单一算子 → 输出

串联模式 A（修正后精简）：
  失败内容 → Revision → 修正内容 → Refinement → 精炼修正内容 → 输出

串联模式 B（合成后精简）：
  多个候选 → Recombination → 重组内容 → Refinement → 精炼重组内容 → 输出

完整闭环模式：
  失败内容 → Revision → 修正方案
                      ↓
  多个候选（含修正方案）→ Recombination → 重组内容
                                          ↓
                                Refinement → 精炼内容 → 输出
```

**Hermes 场景映射**：

| 场景 | 算子 | 价值 |
|------|------|------|
| 代码审查发现 bug | Revision | 自动分析根因 + 生成多种修复方案 |
| Kanban 多 worker 并行结果融合 | Recombination | 合成最优执行路径 |
| 审计报告/长文档精简 | Refinement | 去除冗余 + 风险评估 |
| 文档审计发现事实错误 | Revision | 定位错误 + 生成修正方案 |

**实施优先级**：P0（最核心、最常用、可直接落地）

**预计工时**：1-2 天

### 3.2 第 3 层：数据层（Data Layer）

**核心定位**：轨迹反馈机制，将执行结果转化为可学习的信号。

**来源框架**：CoEvolve（Agent-Data 协同进化）

**核心问题**：第 2 层执行产生的轨迹结果（成功/失败、质量高低）如何被系统吸收，用于优化后续执行？

**核心机制**：

1. **轨迹捕获** — 从第 2 层算子执行结果中提取结构化信号
   - 成功轨迹：记录有效步骤、正确模式、最优参数
   - 失败轨迹：记录失败类型、根本原因、避坑知识

2. **信号转化** — 将轨迹结果转化为可学习的信号
   - 高质量轨迹 → 提升相关记忆的权重
   - 失败轨迹 → 记录失败模式，降低相似路径的优先级
   - 正交方案 → 丰富方案多样性，避免单一路径依赖

3. **分布更新** — 动态调整 Hindsight 记忆库的权重分布
   - 高频成功模式 → 权重提升，检索优先级提高
   - 高频失败模式 → 权重降低，避免重复踩坑
   - 新发现模式 → 权重初始化为中等，待验证后调整

4. **遗忘机制** — 定期清理过时的记忆
   - 长期未使用的记忆 → 权重衰减
   - 已被证明无效的模式 → 标记为废弃
   - 新验证有效的模式 → 权重提升

**输入**：

| 参数 | 类型 | 来源 |
|------|------|------|
| `trajectory_results` | List[TrajectoryResult] | 第 2 层算子执行结果 |
| `success_signals` | List[SuccessSignal] | 成功轨迹的质量评分 |
| `failure_signals` | List[FailureSignal] | 失败轨迹的失败类型 + 根因 |

**输出**：

| 参数 | 类型 | 去向 |
|------|------|------|
| `updated_memory_weights` | Dict[str, float] | Hindsight 记忆库权重更新 |
| `failure_pattern_db` | List[FailurePattern] | 失败模式库（供 Refinement 使用） |
| `distribution_shift_log` | List[DistributionShift] | 分布变化记录 |

**与上下层关系**：

- 向上：接收第 2 层的轨迹结果作为输入
- 向下：将更新后的记忆权重反馈给第 4 层调度器
- 横向：为第 2 层 Refinement 算子提供失败模式库

**实施优先级**：P2（依赖第 2 层先跑起来）

**预计工时**：1-2 周

### 3.3 第 4 层：调度层（Scheduling Layer）

**核心定位**：任务分配优化，根据 Agent 能力画像动态匹配任务。

**来源框架**：SEAL（Agent-Environment 协同进化）

**核心问题**：在 Kanban 多 worker 架构中，如何根据 worker 的历史表现和当前能力，动态分配最适合的任务？

**核心机制**：

1. **能力画像构建** — 基于历史执行轨迹，为每个 worker 构建能力画像
   - 擅长领域：哪些类型的任务成功率高
   - 薄弱领域：哪些类型的任务容易失败
   - 效率特征：平均执行时间、token 消耗、迭代次数

2. **任务特征提取** — 为每个待分配任务提取特征
   - 任务类型：代码审查 / 文档审计 / 数据查询 / 方案编写
   - 难度等级：基于历史同类任务的平均执行时间估算
   - 关键技能：完成任务所需的核心能力

3. **匹配决策** — 将任务特征与 worker 能力画像匹配
   - 高匹配度 → 优先分配
   - 中等匹配度 → 可作为锻炼任务分配
   - 低匹配度 → 避免分配，或搭配高能力 worker 协同

4. **动态调整** — 根据执行结果实时更新能力画像
   - worker 在某类任务上连续成功 → 提升该类任务的匹配权重
   - worker 在某类任务上连续失败 → 降低该类任务的匹配权重
   - worker 展现出新能力 → 更新能力画像

**输入**：

| 参数 | 类型 | 来源 |
|------|------|------|
| `task_pool` | List[Task] | Kanban 待分配任务 |
| `worker_profiles` | Dict[worker_id, Profile] | 第 3 层更新的能力画像 |
| `memory_weights` | Dict[str, float] | 第 3 层更新的记忆权重 |

**输出**：

| 参数 | 类型 | 去向 |
|------|------|------|
| `task_assignments` | Dict[task_id, worker_id] | 任务分配决策 |
| `assignment_rationale` | Dict[task_id, str] | 分配理由（可解释性） |
| `profile_updates` | List[ProfileUpdate] | 需要更新的能力画像变更 |

**与上下层关系**：

- 向上：接收第 3 层的记忆权重和能力画像
- 向下：将分配的任务交给第 2 层 worker 执行
- 横向：与 Kanban 任务板深度集成

**实施优先级**：P2（依赖第 2 层和第 3 层先有数据基础）

**预计工时**：1-2 周

## 四、层间信号流动

### 4.1 信号流向图

```
信号流向（自底向上）：
───────────────────
第 2 层 → 第 3 层：执行轨迹 + 成功/失败信号 → 记忆权重更新
第 3 层 → 第 4 层：更新后的能力画像 + 记忆权重 → 任务分配决策优化

信号流向（自顶向下）：
───────────────────
第 4 层 → 第 2 层：任务分配决策 → worker 执行任务
第 3 层 → 第 2 层：失败模式库 → Refinement 算子风险扫描
```

```
时序图：
─────────────────────────────────────────────────────────────────

时间 →

第 4 层：[任务分配] ──────────────────────────────────────▶
              │
              ▼

              │
              ▼
第 3 层：      [轨迹捕获 + 信号转化 + 分布更新] ───────────▶
              │
              ▼
第 4 层：[能力画像更新 → 下次分配优化] ◀─────────────────

闭环完成，进入下一轮迭代
```

## 七、关键设计决策

| 决策点 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 第 1 层是否纳入 | 纳入 / 排除 | 排除 | 超出当前 Hermes 架构能力范围 |
| 层间耦合度 | 紧耦合 / 松耦合 | 松耦合 | 各层可独立启用/降级，降低系统复杂度 |
| 进化触发 | 实时 / 批处理 | 批处理 | 轨迹进化需要多轨迹数据，批处理更合理 |
| 失败信号来源 | 显式 / 隐式 | 显式 + 隐式 | 显式（工具调用失败）+ 隐式（结果质量评分） |
| 轨迹存储 | 全量 / 压缩 | 压缩存储 | 降低存储成本，Refinement 算子目标 50-80% 缩减 |
| 进化周期 | 每任务 / 每批次 | 每批次 | 第 3 层需要积累一定量轨迹后再更新分布 |

## 八、风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 第 2 层算子效果不达预期 | 整个框架失去基础 | 中 | Phase 1 设置严格的验收标准，不达标不进入 Phase 2 |
| 第 3 层记忆权重更新导致检索质量下降 | 系统性能退化 | 中 | 设置权重变化上限，每次更新不超过±20% |
| 第 4 层调度策略导致任务分配不均 | 某些 worker 过载 | 低 | 设置 worker 负载上限，超额任务自动重分配 |
| 进化循环出现震荡（质量忽高忽低） | 系统不稳定 | 低 | 设置收敛检测，连续 3 轮无改善则暂停进化 |
| 失败模式库持续增长无上限 | 存储和检索成本增加 | 中 | 设置上限（如 1000 条），按时间衰减 + 使用频率淘汰 |

## 九、待验证问题

1. **第 2 层算子的实际效果** — 三大算子在真实场景中的修正/重组/精炼质量如何？需要建立基准测试。
2. **第 3 层记忆权重更新的灵敏度** — 权重变化多少合适？太大导致震荡，太小无效。
3. **第 4 层能力画像的构建成本** — 需要多少历史轨迹才能构建可靠的能力画像？
4. **三层闭环的收敛性** — 是否存在进化震荡或发散的风险？需要什么样的稳定性约束？
5. **Token 消耗与 ROI** — 进化闭环带来的质量提升能否覆盖额外的 LLM 调用成本？
6. **多语言支持** — 当前设计以中文为主，是否需要支持英文/多语言场景？
