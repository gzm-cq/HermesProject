### 2.2 ⚠️ 关键发现：Vestige AGPL 问题

**问题**：Vestige 是 **AGPL-3.0**（不是 Apache/MIT）。AGPL 的"网络交互即分发"条款意味着：
- 通过 HTTP/MCP 远程调用 Vestige server 也可能触发 copyleft
- 不能将 Vestige 代码嵌入到闭源/私有的 HermesProject 中
- 只有在完全隔离的独立进程中运行、不做任何代码修改的情况下风险较低

**建议**：**降级 Vestige 为"借鉴理念"。** 不安装 `vestige-mcp-server`，而是自己实现简版 FSRS-6 遗忘算法：
- 知识导航插件中维护 `access_count` 和 `last_access_time`
- 每 7 天 cron 跑一次衰减：`weight *= 0.9^(days_since_last_access)`
- 低于阈值（0.2）的记忆标记为 `low_priority`，pre_llm_call 时跳过
- 自己实现约 50 行代码，不依赖任何外部包

### 2.4 ⚠️ 关键发现：auto-harness 耦合问题

**问题**：auto-harness 的代码深度绑定在 Terminal-Bench 2.0 基准测试框架中：
- `benchmark.py`(892行): 核心逻辑，但强依赖 Harbor + Docker 沙箱
- `gating.py`(407行): 回归测试门控，依赖 Terminal-Bench 的 verifier 结果格式
- `agent/templates/`(403行): 针对特定 benchmark 的 agent 模板

我们想要的 **Weakness Mining** 模块**不是独立的**——它散布在 benchmark 管线的各个步骤中，不能直接提取。

**建议**：**auto-harness 降级为"借鉴理念"。** 不拷贝源码，而是：
1. 从我们的 `trace.log` 提取失败轨迹（已有 `skillopt-sleep/mine.py` 的 `heuristic_mine` 和 `llm_miner`）
2. 实现 WeaknessMiner 类，聚类失败模式
3. 实现 RegressionTester 类，用已有 Docker 环境跑回归测试
4. 代码量预估：~200 行新代码，全部在 HermesProject 内
