## 三、修正后的详细方案

### 3.1 Graphiti — 知识时效性管理 ⭐⭐⭐⭐⭐（新 P0）

**为什么 Hermes 不会做**：Hermes #346 关注的是记忆的**结构化类型和关系**，不是**时间维度**。Graphiti 的双时态模型（bi-temporal model）追踪事实变更历史，这对企业级知识管理（如配置版本、API Key 过期、模型下线通知）是刚需，但不在 Hermes 的消费级定位中。

**项目地址**：https://github.com/getzep/graphiti

**核心能力**：
- 双时态知识图谱：事实变更时自动失效旧边，保留完整历史
- 增量更新，不需全量重建
- 混合检索：语义 + BM25 + 图遍历，P95 155ms，LoCoMo 94.7%
- 已有 Neo4j 后端支持

**集成方式**：
```
HermesProject 插件 → Graphiti API
    │
    ├─ 写入：知识树中的配置类知识同步时间戳
    ├─ 检索：增加时间维度过滤（"这个事实在 X 日期是否有效"）
    └─ 维护：自动标注过期知识，推送到 Hindsight 降权
```

**改动范围**：
- 新建 `/mnt/d/HermesProject/scripts/graphiti-bridge/` — Graphiti 与知识树的桥接服务
- 修改知识导航插件 — 增加时间维度过滤

**与 Hermes 关系**：互补。Hermes #346 落地后，Graphiti 可视为其时间维度的外挂补充——Hermes 管结构化类型和关系，Graphiti 管时间有效性。

**风险**：Graphiti 是 Zep 的开源框架，Neo4j 依赖，文档不够成熟。

---

### 3.2 Ouroboros 审查模式 — 自修改审查闭环 ⭐⭐⭐⭐（新 P1）

**为什么 Hermes 不会做**：Hermes #337 和 #28767 关注的是**如何进化**，不是**如何审查进化结果**。自修改的安全审查和受保护表面（protected surface）对 Hermes 来说是运行时问题，他们更倾向信任自己的迭代流程。

**项目地址**：https://github.com/razzant/ouroboros（借鉴模式，不部署 runtime）

**核心能力**：
- 多 LLM 独立审查修改提案（3 个 LLM 各自审）
- Protected surface 机制：宪法级规则不可被自动修改
- Git 追踪：每次自动修改生成 commit，可回滚

**集成方式**（不部署 Ouroboros runtime，只提取模式）：
```
SE-Agent Revision 算子产出修正
    │
    ├─ Protected surface 检查：SKILL.md frontmatter 不可改
    ├─ Multi-model review：3 LLM 独立审查 → 投票
    ├─ Git 追踪：自动 commit
    └─ Rollback 路径：git revert
```

**改动范围**：
- 修改 `/mnt/d/HermesProject/scripts/self-evolving/operators/revision.py`
- 修改 `/mnt/d/HermesProject/scripts/self-evolving/operators/refinement.py`

**与 Hermes 关系**：完全独立。Hermes 的进化 loop 产出 PR 让人审，我们的 SE-Agent 自动审查不需要人。

### 3.3 原 P0 项目的替代策略

既然 auto-harness、Cognee、Vestige、MemSkill 与 Hermes roadmap 重叠，不能直接引入，但我们需要**在 Hermes 落地之前**填补缺口：

#### 3.3.1 失败轨迹挖掘（替代 auto-harness）

**不在 HermesProject 外找项目**，而是**强化已有能力**：

```
HermesProject 已有：
  self-evolving/trajectory.py  ← 已有轨迹数据模型（含 failure_points 方法）
  skillopt-sleep/mine.py       ← 已有 heuristic_mine + llm_miner
  skillopt-runner/             ← 已有 SkillOpt 运行器

需要补的：
  trace.log 的失败轨迹 → 统一 FailureTrace JSON Schema
  → 接入 skillopt-sleep 的 llm_miner
  → 产出 WeaknessPattern → 自动优化 SKILL.md
```

**改动**：
- 定义 Hermes 失败轨迹的 JSON Schema → `/mnt/d/HermesProject/scripts/self-evolving/schemas/failure_trace.json`
- 在 `skillopt-runner` 中增加 `weakness_mining` 阶段，调用 llm_miner 从 trace.log 提取模式
- 已有的 SkillOpt 优化循环直接接受这些模式

**与 auto-harness 的关系**：auto-harness 的核心价值（Weakness Mining + 回归测试门控）中，Weakness Mining 我们已有 skillopt-sleep 的 llm_miner 可复用，回归测试门控需要 Docker 沙箱。**不引入新项目，强化已有组件**。

#### 3.3.2 记忆遗忘（替代 Vestige）

**先用 Hermes 现有能力顶住**，等 #346 Phase 4 落地：

```
短期方案（不改 Hermes 源码）：
  cron skill：vestige-weeder（用 session_search 的 FTS5 扫描）
  → 标记 30 天未访问的记忆为 low_priority
  → 在 pre_llm_call 中过滤掉这些标记

长期方案：
  Hermes #346 Phase 4 落地后，自动拥有 importance decay + pruning
```

**改动**：
- 新建 skill：`vestige-weeder`（cron 每天运行）
- 修改知识导航插件：增加 `low_priority` 过滤

#### 3.3.3 知识图谱补全（替代 Cognee）

**等 Hermes #346**，在此之前用 codegraph MCP 作为代码知识图谱的补充：

```
codegraph MCP（已有，端口 4145）
  → codegraph_search / codegraph_explore / codegraph_callers
  → 提供代码层面的事实知识（函数调用关系、文件依赖）

知识树的跨科链接
  → 先实现 knowledge_tree_edges 表（已设计，未实现）
  → 用 codegraph 的代码关系图做"代码知识"的跨科链接
  → 不需要 Cognee
```

## 四、codegraph MCP 在飞轮中的角色

codegraph MCP 是我们已有但**未充分利用**的能力：

| 飞轮层 | codegraph 的用途 | 当前状态 |
|--------|-----------------|---------|
| L1 工具层 | 分析 skill/插件代码结构，辅助失败轨迹定位 | ❌ 未接入 |
| L2 数据层 | 代码知识图谱（函数调用、文件依赖）作为知识树的补充 | ❌ 未接入 |
| L3 调度层 | 分析 worker 代码调用关系，优化拓扑 | ❌ 未接入 |

**具体接入方式**：
- 知识导航插件在 `pre_llm_call` 中增加 codegraph 检索：当查询涉及代码问题时，调用 `mcp__codegraph__codegraph_search` 获取代码结构
- 失败轨迹挖掘时，用 codegraph 定位失败工具调用的源码位置：`codegraph_callers` 找出谁调用了它
- 知识树的知识点如果来自代码（如 API 使用方式、工具参数），关联 codegraph 的 symbol 节点
