## 二、对前一份报告的修正

### ✅ 修正 1：P0-4 codegraph —— 原「应调 MCP 工具」论断已撤回（2026-08-23 实施时订正）
- 前评（初版）：🟢「插件应直接调已连接的 codegraph MCP 工具，而非 subprocess」。
- **实施时订正**：执行方案 SPEC **2.4 节明确写明**——「插件**不能调 Tool Registry（MCP 工具）**，但可以 subprocess 调 CLI」（已向 codegraph 确认）；hook 跑在 `pre_llm_call`（LLM 调用前），无法作为 MCP 工具调用方。故**正确做法就是 SPEC 原定的 subprocess `codegraph query`**，初版「修正 1」论断有误，以此处为准。
- 关于初版担心的「subprocess 争 SQLite 锁」：`codegraph query` 是**只读**操作（WAL 并发读安全），之前 `status` 报 "database is locked" 是写操作，不影响 query。已在 WSL 实测并发调用正常。
- **实施结论**：已于 router.py 落地 `_do_codegraph_recall`（subprocess + timeout=5s）、关键词触发、并入 `kept`、`_assemble_xml_output` 新增 `<knowledge source="codegraph">` 块；config.py 加 `codegraph_*` 配置（含 ENV 覆盖）。WSL 实测：代码 query 命中返回 5 符号 / 0.39s，非代码 query 不触发，XML 渲染正确。

## 六、隐性风险（WSL 视角）

1. **Vestige 与 `scripts/memory-cleanup/` 可能重复建设** → 整合而非另起。
2. **P0-4 应调 MCP 而非 subprocess**：SPEC 的 subprocess 方案需改写，否则会与已运行的 codegraph MCP 争抢 SQLite 锁（实测 Windows 侧 `status` 报 "database is locked" 即因此）。
3. **HF/GitHub/DockerHub 直连超时**：下载类任务一律走镜像（hf-mirror / GitHub 直连可用 / Docker 已配镜像），勿依赖直连。
4. **约束边界（已澄清）**：改动 Hermes 核心**配置文件**（含 MCP server 注册）不破约束；仅禁止改动核心源码逻辑。Cognee 等需注册 MCP 的任务按此口径可正常推进，但仍遵守「最小改动 + 先备份配置」。
