## 三、详细集成方案

### 3.1 auto-harness — 飞轮 L1 闭环 ⭐⭐⭐⭐⭐

**缺口**：当前飞轮 L1 的三大算子修正的是"这次做错了什么"，但缺少"系统地从失败轨迹中挖掘模式→优化 skill 和插件"。SkillOpt-Runner 只优化 SKILL.md 文本，不能改代码。

**项目地址**：https://github.com/neosigmaai/auto-harness

**核心原理**：
```
失败轨迹 → Weakness Mining（聚类+模式提取）→ Harness Proposal（修改提案）
→ Validation（回归测试门控）→ Accept/Reject
```

**集成方式**：
```
Hermes 失败轨迹（trace.log + session DB）
    │
    ▼
auto-harness 的 Weakness Mining
    │ 聚类失败轨迹，提取模式
    ▼
Harness Proposal
    │ 提案 = 修改 HermesProject 的 skill/插件代码
    ▼
Validation（Docker 沙箱运行回归测试）
    │
    ├─ PASS → deploy 到 HermesProject
    └─ FAIL → 丢弃，记录 pattern 到失败模式库
```

**改动范围**：
- 新建 `/mnt/d/HermesProject/scripts/auto-harness/` — 迁移 auto-harness 源码
- 修改 `/mnt/d/HermesProject/plugins/knowledge-navigation/` — 增加失败轨迹输出接口
- 新增 skill 文件：`auto-harness-runner`（cron 定时触发）

**依赖**：
- Docker（已有）
- Harbor 可选（不必须，可用 Docker backend 替代）
- 需要为 Hermes 的失败轨迹定义统一的 JSON 格式

**实现步骤**：
1. 克隆 auto-harness，提取核心 Weakness Mining 模块（不依赖 Harbor 的部分）
2. 定义 Hermes 失败轨迹的 JSON Schema（工具调用失败、LLM 回复格式错误、任务超时等）
3. 实现 `WeaknessMiner` 类，输入 trace.log + session 失败记录，输出聚类后的 weakness pattern
4. 实现 `HarnessProposer` 类，将 weakness pattern 转化为 skill 修改提案（SKILL.md patch）
5. 实现 `SkillValidator` 类，用 Docker 沙箱跑回归测试验证修改不退化
6. 集成到现有的 SkillOpt-Runner 中，作为其前置环节

**验证指标**：
- 每次迭代后 Skill 的通过率变化
- 失败模式库的覆盖率增长
- 回归测试门控的误报率

### 3.2 Cognee — 知识图谱补全 ⭐⭐⭐⭐⭐

**缺口**：知识树已有树结构（parent_id 二叉），但缺少跨科链接边（`knowledge_tree_edges` 表设计但未实现）。Cognee 的 ECL 管线能自动从文档中提取实体关系并构建知识图谱，14 种检索模式远超当前单一向量召回。

**项目地址**：https://github.com/topoteretes/cognee

**核心原理**：ECL 管线（Extract-Cognify-Load）→ 知识图谱，支持 MCP 协议

**集成方式**：
```
Hermes → MCP server → Cognee
  │                      │
  │                       ├─ 知识图谱存储
  │                       └─ 14 种检索模式
  │
  └─ HermesProject 插件调用 Cognee 的检索结果
```

**改动范围**：
- 修改 `config.yaml` — 添加 `mcp_servers.cognee` 条目（MCP 接入，0 代码改动）
- 可选：修改知识导航插件，在召回时增加 Cognee 检索结果作为补充源

**依赖**：
- Docker 部署 Cognee server（或直接 pip install 作为 Python 库）
- 嵌入模型（可复用现有的 bge-m3）

**实现步骤**：
1. `hermes mcp add cognee --url http://127.0.0.1:8000/mcp` 一行命令接入
2. 接入后验证：`mcp__cognee__search(query="跨科检索测试")` 看返回质量
3. 如果效果好，修改知识导航插件的 `pre_llm_call`，在现有召回之外增加 Cognee 检索结果
4. 对比接入前后跨科知识召回的 recall@5 指标

**验证指标**：
- 跨科知识召回 recall@5 提升
- 对比知识树（纯树）+ Cognee（图）的组合效果 vs 单一树结构

### 3.3 Vestige — 遗忘机制 ⭐⭐⭐⭐⭐

**缺口**：Hindsight 记忆只增不减（24K+ 条累积），无遗忘机制。SE-Agent 设计中规划的"时间衰减 λ=0.1"从未落地。Vestige 的 FSRS-6 间隔重复算法是最成熟的遗忘策略实现。

**项目地址**：https://github.com/samvallad33/vestige

**核心原理**：
- FSRS-6 间隔重复：21 参数模型，根据使用频率自动调整记忆权重
- Prediction-Error Gating：只存新信息，自动合并冗余、覆盖矛盾
- 单 Rust 二进制 22MB，本地 SQLite

**集成方式**：
```
npm install -g vestige-mcp-server  →  stdio MCP server
                                        │
                                        ▼
Hermes config.yaml 加 mcp_servers.vestige 条目
                                        │
                                        ▼
HermesProject 创新 skill：vestige-weeder
  → 定时扫描 Hindsight 记忆，调用 Vestige 评估记忆强度
  → 低于阈值的记忆：降权而非删除（保留原始数据，降低检索优先级）
```

**改动范围**：
- 修改 `config.yaml` — 添加 mcp_servers.vestige 条目
- 新建 skill — `vestige-weeder`（cron 定时任务）
- 新建脚本 — `/mnt/d/HermesProject/scripts/vestige-weeder/`（Hindsight 记忆评分服务）

**依赖**：
- Node.js（已有，用于 npm install）
- 首次运行需下载 embedding 模型（~80MB，一次性的）

**实现步骤**：
1. `npm install -g vestige-mcp-server` 安装
2. 在 `config.yaml` 中添加 `mcp_servers.vestige` 的 stdio 配置
3. 创建 `vestige-weeder` skill，cron 每天运行一次：
   - 从 Hindsight 读取最近 30 天未被访问的记忆
   - 发送给 Vestige 评估 retention score
   - 得分 < 0.2 的记忆：标记为 `low_priority`，pre_llm_call 时跳过
   - 保留原始数据不删除，支持恢复
4. 验证：人工抽查被降权的记忆是否合理

**验证指标**：
- 注入上下文的记忆数量降低（token 节省）
- 被降权的记忆不包含高价值信息（人工抽查）

### 3.4 MemSkill — 记忆策略进化 ⭐⭐⭐⭐

**缺口**：当前 Hindsight recall 是固定的三路并行（semantic + BM25 + graph），权重和策略从不改变。MemSkill 的 controller 能学习"什么场景用什么召回策略"，让记忆操作本身可进化。

**项目地址**：https://github.com/ViktorAxelsen/MemSkill

**核心原理**：将记忆管理重构为"controller 选择技能 + executor 执行技能"的双层架构，controller 从交互中学习策略。

**集成方式**：
```
Hermes query → 知识导航插件 pre_llm_call
                    │
                    ▼
        MemSkill Controller（MCP server）
                    │ 根据 query 类型选择召回策略
                    ▼
        ┌───────┬───────┬────────┐
        │ semantic │ BM25  │ graph  │（权重动态调整）
        └───────┴───────┴────────┘
                    │
                    ▼
        Hindsight recall（现有，不变）
```

**改动范围**：
- 安装 MemSkill 为 MCP server（需封装为 Python 微服务）
- 修改知识导航插件 — 调用 MemSkill controller 获取召回策略权重

**依赖**：
- HuggingFace controller weights（已发布）
- 需要少量标注数据做 eval（~50 条 query + 期望召回策略）

**前提**：需要先建立 eval 数据集，对比"固定策略 vs MemSkill 自适应策略"的效果

**风险**：HuggingFace weights 是基于通用场景训练的，直接迁移到我们领域可能效果不佳，需要 fine-tune

**实现步骤**：
1. 克隆 MemSkill，下载 HuggingFace controller weights
2. 封装为 Python 微服务，暴露 MCP 接口
3. 从 trace.log 提取 50 条典型 query，人工标注"这个场景应该用什么召回策略"
4. 对比：固定策略 vs MemSkill 自适应策略的 recall@5
5. 如果效果好，将 controller 嵌入知识导航插件

### 3.5 Graphiti — 知识时效性管理 ⭐⭐⭐

**缺口**：配置类/版本类知识（API key、端口、模型名）在记忆中不断累积过期信息，当前靠 MEMORY.md 手工维护。Graphiti 的双时态模型能自动处理"这个事实什么时候过期"。

**项目地址**：https://github.com/getzep/graphiti

**核心原理**：双时态知识图谱，事实变更时自动失效旧边，不需全量重建。支持语义 + BM25 + 图遍历三种检索。

**集成方式**：
```
HermesProject 插件 → Graphiti API（跟踪知识时效性）
    │
    ▼
Neo4j 存储知识图谱（Docker 已有）
    │
    ▼
知识导航插件在检索时增加时间维度过滤
```

**改动范围**：
- 新建 `/mnt/d/HermesProject/scripts/graphiti-bridge/` — Graphiti 与知识树的桥接服务
- 修改知识导航插件 — 增加时间维度过滤

**依赖**：
- Neo4j Docker（已有基础）
- Graphiti Python 包（`pip install graphiti`）

**风险**：Graphiti 是 Zep 提供的开源框架，文档不够完善，生产部署经验少

### 3.6 EvoAgentX — 工作流拓扑进化 ⭐⭐⭐

**缺口**：当前 Kanban worker 调度是静态的（developer/researcher/writer 等固定角色），工作流拓扑靠人工设计。EvoAgentX 的 TextGrad/AFlow 算法能自动优化工作流拓扑。

**项目地址**：https://github.com/EvoAgentX/EvoAgentX

**集成方式**：不碰 Kanban 核心代码，EvoAgentX 作为独立脚本运行，优化 worker profile 配置：

```
EvoAgentX 优化脚本
    │
    ├─ 输入：历史任务配置 + 执行结果
    ├─ 进化：调整 worker 组合、角色参数
    └─ 输出：优化后的 profile 配置 → 写入 config.yaml
```

**改动范围**：
- 新建 `/mnt/d/HermesProject/scripts/evoagentx-bridge/` — EvoAgentX 适配脚本
- 修改 `config.yaml` 的 profiles 段（受 EvoAgentX 优化输出影响）

**限制**：EvoAgentX 优化的是 prompt 和拓扑，但 Hermes 的 worker 拓扑（orchestrator → leaf）是固定的，我们能改的只有**每个 worker 的 skill 组合和参数配置**。优化范围受限。

### 3.7 Ouroboros — 自修改审查模式 ⭐⭐⭐

**缺口**：SE-Agent 的 Revision 算子产出修正后，自动审查 + 可回溯的闭环缺失。Ouroboros 的 multi-model review + protected surface 模式可复用。

**项目地址**：https://github.com/razzant/ouroboros

**集成方式**：不部署 Ouroboros runtime，只提取其**设计模式**：

```
Revision 算子产出修正 → 多 LLM 审查（借鉴 Ouroboros review）→ Git 追踪
    │
    ├─ Protected surface：SKILL.md frontmatter 不可改
    ├─ Multi-model review：3 个 LLM 独立审查修改
    └─ Git 追踪：每次自动修改生成 commit
```

**改动范围**：
- 修改 `/mnt/d/HermesProject/scripts/self-evolving/operators/revision.py` — 增加审查环节
- 修改 `/mnt/d/HermesProject/scripts/self-evolving/operators/refinement.py` — 增加 protected surface 检查

**风险**：自修改代码风险高，Ouroboros 曾发生 $2000/24h 失控事件。只提取审查模式，不部署自修改 loop。

---

### 3.8 OpenViking — 统一上下文管理 ⭐⭐

**缺口**：上下文碎片化——memory 在 Hindsight、RAG 在 SAG、知识在知识树，各自独立。OpenViking 的 L0/L1/L2 分层加载和文件系统范式能统一管理。

**项目地址**：https://github.com/volcengine/OpenViking

**问题**：Hermes 已有原生 OpenViking memory provider，但：
- 需要改 Hermes 源码才能修复 issue #5721（启动不可达永久失效）
- 我们已有 Hindsight + 知识树 + SAG 三套，OpenViking 再叠一层会冗余
- 除非我们完全迁移到 OpenViking 替代 Hindsight，否则性价比低

**行动建议**：暂缓。等知识树 + Cognee 跑通后，如果有"统一管理"的需求再评估。

## 五、实施路线图

### 第一批（P0 — 立即动手，高可行度）

| 序号 | 项目 | 工时 | 依赖 | 产出 |
|------|------|------|------|------|
| 1 | Vestige MCP 接入 | 0.5天 | npm install | `vestige-weeder` skill 运行，Hindsight 开始降权低价值记忆 |

| 3 | auto-harness 核心 | 3天 | 无 | WeaknessMiner 跑通，能从 trace.log 提取失败模式 |

**第一批理由**：三个项目都是 MCP 接入或独立脚本，不改任何现有代码的稳定路径，风险最低。Vestige 和 Cognee 是"装上就能用"，auto-harness 需要写适配代码但全部在 HermesProject 内。

### 第二批（P1 — 需要评估后动手）

| 序号 | 项目 | 工时 | 依赖 | 产出 |
|------|------|------|------|------|

| 5 | auto-harness 完整 | 2天 | 第一批完成 | 完整闭环：失败→挖模式→改 skill→回归测试→部署 |
| 6 | Ouroboros 审查模式 | 1天 | 无 | Revision 算子增加多 LLM 审查 + Git 追踪 |

### 第三批（P2 — 可选增强）

| 序号 | 项目 | 工时 | 依赖 | 产出 |
|------|------|------|------|------|
| 7 | Graphiti 时效性 | 2天 | Neo4j | 配置类知识自动过期管理 |
| 8 | EvoAgentX 优化 | 2天 | 第一批 | worker profile 优化建议 |

### 时间线

```
Week 1: [Vestige] [Cognee] [auto-harness WeakenessMiner]
Week 2: [auto-harness 完整闭环] [MemSkill eval]
Week 3: [Ouroboros 审查模式] [Graphiti 可选]
```

## 六、风险与注意事项

| 风险 | 项目 | 缓解措施 |
|------|------|---------|
| Hermes 升级覆盖 MCP 配置 | 全部 MCP 项目 | 在 HermesProject 写 setup 脚本，升级后自动重配 |
| 失败轨迹格式不统一 | auto-harness | 定义统一的 FailureTrace JSON Schema，作为 HermesProject 标准 |
| MemSkill 权重迁移效果差 | MemSkill | 先做 eval 再决定是否集成，不做无验证的投入 |
| Rust 编译环境缺失 | Vestige | 用 npm install 预编译包，不需要 Rust 工具链 |
| 知识图谱数据膨胀 | Cognee | 设置 retention 策略，定期清理低价值边 |

## 七、总结

| 优先级 | 项目 | 一句话判断 |
|--------|------|-----------|
| **P0** | Vestige | npm install 就能解决 Hindsight 遗忘问题，性价比最高 |
