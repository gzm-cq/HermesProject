## 四、RealRoute 移除说明

**审核发现**：RealRoute（arXiv 2604.20860）的 GitHub 代码仓库不存在，仅有论文。更关键的是，代码审计发现**我们的 router.py 已实现论文描述的核心能力**：

| 维度 | RealRoute 论文 | 我们已有的 router.py |
|------|---------------|-------------------|
| 并行检索 | 并行查所有源 | ✅ `_recall_executor.submit()` 四路并行（Hindsight+KT+Skill+SAG） |
| 超时预算 | Adaptive Cap 动态证据预算 | ✅ `_deadline` 绝对截止时间 + `_left()` 剩余预算计算 |
| 熔断保护 | 未描述 | ✅ `circuit_is_open` / `circuit_record_failure` 熔断器 |
| 去重 | 统一证据池去重 | ✅ `_dedup_by_text()` + turn-to-turn 降权 |
| 日志追踪 | 验证链可视化 | ✅ `recall_logger.record()` 每路独立记录 |
| Token 观测 | 未描述 | ✅ 按源统计 token 消耗 |

**结论**：引入 RealRoute 不仅无增量价值，反而可能因自实现引入退化。**知识导航路由不需要外部项目**，当前 `router.py`（1252 行）已具备完整的多源并行召回、熔断、去重、日志能力。

### 6.1 SkillRouter — Skill 语义召回（拷贝源码）⭐⭐⭐⭐⭐

**项目地址**：https://github.com/zhengyanzhao1997/SkillRouter (MIT, 235 ⭐)
**论文**：arXiv 2603.22455
**HuggingFace 模型**：`pipizhao/SkillRouter-Embedding-0.6B` + `pipizhao/SkillRouter-Reranker-0.6B`

**现状问题**：Hermes 的 `available_skills` 列表约 110 个，靠名称匹配，无语义检索、无重排。

**核心思路**：
```
第一阶段：bi-encoder 检索
  query → SR-Emb-0.6B → 从 skill 池召回 top-20

第二阶段：cross-encoder reranker
  top-20 → SR-Rank-0.6B → 重排 → top-1 或 top-5
```

**集成方式**：拷贝 `src/` 下 7 个 Python 文件（共 663 行）到 `scripts/skill-router/`
- `run_open_model_eval.py`（227 行）— 主推理逻辑
- `common.py`（134 行）— 公共工具
- `export_retrieval.py`（63 行）— 检索导出
- `evaluate_predictions.py`（84 行）— 评估
- `metrics.py`（69 行）— 指标计算
- `data_io.py`（56 行）— 数据 IO

**注意**：SkillRouter 不是替换 `_do_skill_match` 的调用方，而是替换 `skill_matcher` 的 embedding 层。
当前 `_do_skill_match`（router.py:308）→ `skill_matcher.match_skills(query)` 是三阶段匹配（keyword → embedding → LLM）。SkillRouter 替换其中的 **embedding 阶段**：从当前 bge-m3 的 embedding 匹配升级为两阶段检索（bi-encoder + reranker）。

**改动范围**：
- 新建 `/mnt/d/HermesProject/scripts/skill-router/` — 拷贝推理代码
- 修改 `skill_matcher.py` — 替换 embedding 层为 SkillRouter 的 bi-encoder + reranker

**依赖**：0.6B 模型约 1.2GB 内存，WSL2 CPU 可运行

### 6.7 codegraph — 代码知识检索（已有服务接入飞轮）⭐⭐⭐⭐⭐

**当前状态**：codegraph 已安装，MCP server 模式运行（端口 4145），但未接入飞轮。

**集成方式**：不走 MCP/HTTP 桥，插件用 **subprocess 调 CLI** 直接查询：
```python
import subprocess, json

def _do_codegraph_recall(query: str) -> list[dict]:
    """codegraph CLI 直接查询，不走 MCP 桥，无连接泄漏"""
    result = subprocess.run(
        ["codegraph", "query", query, "--json", "--limit", "5",
         "--path", "/mnt/d/HermesProject"],
        capture_output=True, text=True, timeout=5
    )
    if result.returncode != 0:
        return []
    return json.loads(result.stdout)
```

**为什么不走 MCP/HTTP 桥**：SSE 桥有历史连接泄漏问题（三个 bug 叠加：proc 句柄丢失、future 泄漏、SSE 流未关闭）。CLI subprocess 每次调用独立进程，退出即释放，零泄漏风险。

**接入位置**：加在 `_execute_recall`（router.py:541）内部，作为**条件性调用**——不是加在 `pre_llm_call` 入口，而是在 `_execute_recall` 的串行分支（router.py:675 的 `else` 块）之后或并行分支的 `finally` 之后。query 涉及代码时（关键词匹配触发），调 `subprocess.run(["codegraph", "query", ...])`，否则跳过。

**集成方式**：
- 知识导航 `_execute_recall` 增加 codegraph 条件性查询：query 涉及代码时用关键词匹配触发
- 失败轨迹挖掘时，用 `codegraph query --kind function` 定位失败工具调用的源码位置
- 知识树知识点如来自代码，关联 codegraph symbol 节点

**改动范围**：修改知识导航插件 `router.py` 的 `_execute_recall`，约 15 行
