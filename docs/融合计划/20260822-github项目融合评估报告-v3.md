> 日期：2026-08-22 | V3.0

## 一、边界界定

```
┌─────────────────────────────────────────────────────────────────────┐
│  Hermes 官方（不改，每天升级）                                         │
│  Hermes 核心源码 + Hindsight 记忆系统 + 官方插件(memory provider等)    │
└───────────────────────────┬──────────────────────────────────────────┘
                            │ 依赖/调用
┌───────────────────────────▼──────────────────────────────────────────┐
│  HermesProject（我们的项目，可改）                                      │
│                                                                       │
│  插件层：knowledge-navigation / knowledge-tree-plugin                  │
│  脚本层：self-evolving / skillopt-runner / skillopt-sleep / clustering  │
│  配置层：MCP server / worker profile / Skill 文件                      │
│                                                                       │
│  数据飞轮三层：                                                         │
│    L1 工具层：三大算子（Revision/Recombination/Refinement）             │
│    L2 数据层：Hindsight（官方）+ 知识树（我们的）+ SAG（我们的）         │
│    L3 调度层：Kanban（官方）+ worker profile（我们的）                   │
└───────────────────────────────────────────────────────────────────────┘
```

**关键认知**：Hermes 官方做的是**通用核心能力**（#337 优化 pipeline、#346 结构化记忆、#553 后台观察者）。我们在 HermesProject 层面做的是**把这些能力接入我们的飞轮**，并在官方能力未覆盖的地方做我们自己的增强。两者不矛盾。

## 二、Hermes 官方 roadmap 对照

查阅 Hermes GitHub Issues，以下官方规划与我们的飞轮方向相关：

| Issue | 官方做什么 | 对我们的影响 |
|-------|----------|------------|
| **#337** Evolutionary Self-Improvement | DSPy+GEPA 优化 SKILL.md 的通用 pipeline，独立 repo (5.1k ⭐) | 官方提供优化引擎，**我们的 skillopt-runner 提供飞轮场景**——我们要做的是把失败轨迹喂给这个引擎 |
| **#346** Structured Memory System | typed nodes + graph edges + FTS5+vector+graph hybrid search | 官方重构记忆系统，**我们的知识树是独立于官方记忆的补充层**——可以并存 |
| **#553** Subconscious Observer | 后台记忆处理 + 跨会话模式检测 | 官方做后台处理，**我们的知识导航插件做实时召回**——前端召回和后台处理不冲突 |

**结论**：官方做通用能力，我们做飞轮场景接入。不是"重叠就放弃"，而是"官方提供什么能力，我们在 HermesProject 层面接入到飞轮中"。

## 四、详细方案

### 4.1 auto-harness — 失败轨迹挖掘（🟡 接入）⭐⭐⭐⭐⭐

**Hermes 官方对应**：#337 (DSPy+GEPA 优化 pipeline)

**不重叠的理由**：官方 #337 做的是"怎么优化"——DSPy+GEPA 引擎怎么跑。我们做的是"优化什么"——从飞轮的失败轨迹中提取什么模式喂给优化引擎。auto-harness 的 Weakness Mining 模式增强的是**我们的 skillopt-runner 的输入端**，不是跟 #337 抢优化引擎。

**项目地址**：https://github.com/neosigmaai/auto-harness

**核心原理**：
```
失败轨迹 → Weakness Mining（聚类+模式提取）→ Harness Proposal（修改提案）
→ Validation（回归测试门控）→ Accept/Reject
```

**集成方式**：
```
Hermes 失败轨迹（trace.log + session DB）
    │
    ▼
auto-harness 的 Weakness Mining 模式
    │ 聚类失败轨迹，提取 weakness pattern
    ▼
接入我们的 skillopt-sleep/llm_miner
    │ llm_miner 已有从 session 提取 TaskRecord 的能力
    │ auto-harness 补的是"从失败轨迹提取 weakness pattern"这一步
    ▼
SkillOpt 优化循环（我们的 skillopt-runner）
    │ 或者 Hermes #337 落地后，喂给官方 DSPy+GEPA
    ▼
SKILL.md 修改提案
    │
    ├─ PASS → deploy 到 HermesProject
    └─ FAIL → 丢弃，记录 pattern 到失败模式库
```

**改动范围**：
- 新建 `/mnt/d/HermesProject/scripts/auto-harness/` — 提取 auto-harness 的 Weakness Mining 模块
- 修改 `skillopt-sleep/mine.py` — 增加 `weakness_mine` 函数，从 trace.log 提取失败模式
- 新增 skill：`auto-harness-runner`（cron 定时触发）

**依赖**：Docker（已有），不需要 Harbor（用 Docker backend 替代）

**验证指标**：每次迭代后 Skill 通过率变化、失败模式库覆盖率

### 4.2 Cognee — 知识图谱补全（🟡 接入）⭐⭐⭐⭐⭐

**Hermes 官方对应**：#346 (Structured Memory System — typed nodes + graph edges + hybrid search)

**不重叠的理由**：#346 重构的是 Hermes 的**官方记忆系统**（MEMORY.md → SQLite typed nodes）。我们的知识树是 HermesProject 层面的**独立知识层**，不在官方记忆系统里。Cognee 补的是我们知识树的跨科链接边（`knowledge_tree_edges` 表已设计未实现），跟 #346 的 graph edges 是两套系统。

**项目地址**：https://github.com/topoteretes/cognee (30.1k ⭐)

**核心能力**：ECL 管线（Extract-Cognify-Load）→ 知识图谱，14 种检索模式，支持 MCP

**集成方式**：
```
Hermes → MCP server → Cognee
  │
  ├─ 官方记忆（#346 落地后）：typed nodes + graph edges（Hermes 官方管理）
  │
  └─ 我们的知识树：Cognee 补充跨科链接边 + 14 种检索模式
     ├─ 知识树结构（parent_id 二叉）= 我们的
     ├─ 跨科链接边（knowledge_tree_edges）= Cognee 补的
     └─ 混合检索 = Cognee 的 14 种模式
```

**改动范围**：
- 修改 `config.yaml` — 添加 `mcp_servers.cognee` 条目（MCP 接入，0 代码改动）
- 可选：修改知识导航插件，在召回时增加 Cognee 检索结果作为补充源

**依赖**：Docker 部署 Cognee server（或 pip install），嵌入模型复用 bge-m3

**验证指标**：跨科知识召回 recall@5 提升

### 4.3 Vestige — 遗忘机制（🟡 接入）⭐⭐⭐⭐⭐

**Hermes 官方对应**：#346 Phase 4 (importance decay + pruning + 30 天清除)

**不重叠的理由**：#346 Phase 4 是 Hermes **官方记忆系统**的遗忘。我们的知识树和 SAG 里的知识也需要遗忘，但不在 #346 的范围内。Vestige 跑在 HermesProject 插件层，管我们自己的知识降权，等 #346 落地后两边自然衔接。

**项目地址**：https://github.com/samvallad33/vestige (607 ⭐)

**核心能力**：FSRS-6 间隔重复（21 参数），prediction-error gating，单 Rust 二进制 22MB

**集成方式**：
```
npm install -g vestige-mcp-server → stdio MCP server
    │
    ├─ Hermes 官方记忆（#346 Phase 4 落地后）：官方 importance decay
    │
    └─ 我们的 vestige-weeder skill：
       → 扫描知识树 + SAG 中 30 天未访问的知识
       → 调用 Vestige 评估 retention score
       → 得分 < 0.2 的知识：标记 low_priority，pre_llm_call 时跳过
       → 保留原始数据不删除，支持恢复
```

**改动范围**：
- 修改 `config.yaml` — 添加 `mcp_servers.vestige` 条目
- 新建 skill：`vestige-weeder`（cron 每天）
- 修改知识导航插件 — 增加 `low_priority` 过滤

**依赖**：Node.js（已有），首次下载 embedding 模型 ~80MB

### 4.4 MemSkill — 记忆策略进化（🟡 接入）⭐⭐⭐⭐

**Hermes 官方对应**：#346 + #553 (Subconscious Observer — 后台记忆处理)

**不重叠的理由**：#553 做的是**后台**记忆处理和跨会话模式检测。我们的知识导航插件做的是**实时**召回策略选择。MemSkill 的 controller 可以让我们的 pre_llm_call 根据查询类型动态选择召回策略，跟 #553 的后台处理是前后端关系。

**项目地址**：https://github.com/ViktorAxelsen/MemSkill

**核心能力**：controller 学习选择记忆技能 + executor 执行技能，已发布 HuggingFace controller weights

**集成方式**：
```
Hermes query → 知识导航插件 pre_llm_call
                    │
                    ▼
        MemSkill Controller（MCP server）
                    │ 根据 query 类型选择召回策略
                    ▼
        ┌───────┬───────┬────────┐
        │ semantic │ BM25  │ graph  │（权重动态调整）
        └───────┴───────┴────────┘
                    │
                    ▼
        Hindsight recall + 知识树 + SAG（现有，不变）
```

**改动范围**：
- 封装 MemSkill 为 MCP server
- 修改知识导航插件 — 调用 controller 获取召回策略权重

**前提**：先建 eval 数据集（~50 条 query + 期望召回策略），对比固定策略 vs 自适应

**风险**：HuggingFace weights 通用场景训练，可能需 fine-tune

### 4.5 Graphiti — 知识时效性管理（🟢 独创）⭐⭐⭐⭐⭐

**Hermes 官方对应**：无

**独创的理由**：Hermes #346 关注记忆的**结构化类型和关系**，不是**时间维度**。双时态知识图谱追踪事实变更历史，这对企业级知识管理（配置版本、API Key 过期、模型下线）是刚需，不在 Hermes 消费级定位中。

**项目地址**：https://github.com/getzep/graphiti

**核心能力**：
- 双时态知识图谱：事实变更时自动失效旧边，保留完整历史
- 增量更新，不需全量重建
- 混合检索：语义 + BM25 + 图遍历，P95 155ms，LoCoMo 94.7%

**集成方式**：
```
HermesProject 插件 → Graphiti API
    │
    ├─ 写入：知识树中的配置类知识同步时间戳
    ├─ 检索：增加时间维度过滤（"这个事实在 X 日期是否有效"）
    └─ 维护：自动标注过期知识，推送到 Hindsight 降权
```

**改动范围**：
- 新建 `/mnt/d/HermesProject/scripts/graphiti-bridge/` — Graphiti 桥接服务
- 修改知识导航插件 — 增加时间维度过滤

**依赖**：Neo4j Docker（已有基础），`pip install graphiti`

### 4.6 EvoAgentX — 工作流拓扑优化（🟡 接入）⭐⭐⭐

**Hermes 官方对应**：#28767 (Self-Evolving Agent Roles via Skill Clustering)

**不重叠的理由**：#28767 做的是**官方** agent 角色的自动进化。我们的 worker profile 是 HermesProject 层面的配置，EvoAgentX 可以优化我们的 profile 配置（每个 worker 的 skill 组合和参数），接受 #28767 的输出作为输入。

**项目地址**：https://github.com/EvoAgentX/EvoAgentX (3.2k ⭐)

**集成方式**：作为独立脚本运行，优化 worker profile 配置：
```
EvoAgentX 优化脚本
    │
    ├─ 输入：历史任务配置 + 执行结果
    ├─ 进化：TextGrad/AFlow 调整 worker skill 组合
    └─ 输出：优化后的 profile 配置 → 写入 config.yaml
```

**改动范围**：
- 新建 `/mnt/d/HermesProject/scripts/evoagentx-bridge/`
- 修改 `config.yaml` 的 profiles 段

**限制**：优化范围受限——Hermes 的 worker 拓扑（orchestrator → leaf）是固定的，我们只能改 worker 的 skill 组合和参数

### 4.7 Ouroboros — 自修改审查模式（🟢 独创）⭐⭐⭐⭐

**Hermes 官方对应**：无

**独创的理由**：Hermes #337 和 #28767 关注的是**如何进化**，不是**如何审查进化结果**。自修改的安全审查和 protected surface 对 Hermes 来说是运行时问题，他们倾向信任迭代流程。我们的 SE-Agent 算子需要这层审查。

**项目地址**：https://github.com/razzant/ouroboros (4.9k ⭐)（借鉴模式，不部署 runtime）

**集成方式**（只提取设计模式）：
```
SE-Agent Revision 算子产出修正
    │
    ├─ Protected surface 检查：SKILL.md frontmatter 不可改
    ├─ Multi-model review：3 LLM 独立审查 → 投票
    ├─ Git 追踪：自动 commit
    └─ Rollback 路径：git revert
```

**改动范围**：
- 修改 `/mnt/d/HermesProject/scripts/self-evolving/operators/revision.py` — 增加审查环节
- 修改 `/mnt/d/HermesProject/scripts/self-evolving/operators/refinement.py` — 增加 protected surface 检查

## 五、codegraph MCP 在飞轮中的角色

codegraph MCP（端口 4145，已有服务）是我们已有但**未充分利用**的能力：

| 飞轮层 | codegraph 用途 | 当前状态 |
|--------|---------------|---------|
| L1 工具层 | 分析 skill/插件代码结构，辅助失败轨迹定位 | ❌ 未接入飞轮 |
| L2 数据层 | 代码知识图谱（函数调用、文件依赖）作为知识树补充 | ❌ 未接入飞轮 |
| L3 调度层 | 分析 worker 代码调用关系，优化拓扑 | ❌ 未接入飞轮 |

**具体接入方式**：
- 知识导航插件 `pre_llm_call` 增加 codegraph 检索：查询涉及代码问题时调用 `codegraph_search`
- 失败轨迹挖掘时，用 `codegraph_callers` 定位失败工具调用的源码位置
- 知识树知识点如果来自代码（API 使用、工具参数），关联 codegraph 的 symbol 节点
