# 四层进化闭环设计

> **文档版本**: v1.0  
> **创建时间**: 2026-05-29  
> **状态**: 待验证草案（设计阶段，未实施）  
> **参考来源**: SEAL (arXiv:2605.24426) · SE-Agent (arXiv:2508.02085) · CoEvolve (arXiv:2604.15840)

---

## 一、设计目标

构建一个**四层进化闭环框架**，将 SEAL、SE-Agent、CoEvolve 三个代表性工作的进化机制融合为一个统一架构，实现从环境到模型参数的全链路自进化能力。

**核心问题**：单一进化机制存在局限——SEAL 只优化环境、CoEvolve 只优化数据分布、SE-Agent 只优化推理轨迹。三者互补但各自孤立，缺乏统一框架。

**设计原则**：
- 每层有明确的进化界面和输入输出边界
- 层与层之间形成数据/信号流动链
- 下层为上层提供优化目标，上层为下层提供反馈信号
- 可独立启用/降级，不强制全量运行

## 二、四层架构总览

```
┌──────────────────────────────────────────────────────────────────┐
│                    四层进化闭环（自顶向下）                        │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  第 4 层：环境进化 ──────▶ 优化任务界面                           │
│  (SEAL)                    输入：任务集合                         │
│                            输出：进化后的任务分布                  │
│                                │                                 │
│                                ▼                                 │
│  第 3 层：分布进化 ──────▶ 优化训练数据                           │
│  (CoEvolve)                  输入：失败信号 + 任务               │
│                            输出：更新后的数据分布                  │
│                                │                                 │
│                                ▼                                 │
│  第 2 层：轨迹进化 ──────▶ 优化推理策略                           │
│  (SE-Agent)                  输入：失败轨迹 + 轨迹池              │
│                            输出：精炼后的最优轨迹                  │
│                                │                                 │

│  (RL/GRPO)                   输入：轨迹质量信号                   │
│                            输出：更新后的模型权重                  │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## 三、各层详细设计

### 第 4 层：环境进化（Environment Evolution）

**来源框架**：SEAL（西湖大学 + 蚂蚁集团）

**核心思想**：Agent 与环境协同进化。环境不是静态的任务集合，而是根据 Agent 的表现动态调整任务难度和分布。

**进化界面**：训练环境（粗粒度）

**输入**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `task_pool` | List[Task] | 当前任务池 |
| `agent_performance` | Dict[str, float] | Agent 在各任务上的表现评分 |
| `difficulty_curve` | Curve | 任务难度分布曲线 |

**输出**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `evolved_task_pool` | List[Task] | 进化后的任务池 |
| `difficulty_adjustment` | Dict | 难度调整记录 |
| `novelty_score` | float | 新任务新颖度评分 |

**进化机制**：
1. **失败驱动任务生成** — 当 Agent 在某类任务上持续失败，环境自动生成该类型的变体任务
2. **难度自适应** — 根据 Agent 成功率动态调整任务难度（类似课程学习）
3. **多样性注入** — 定期引入与现有任务语义不同但技能相关的新型任务

**与下层关系**：
- 向第 3 层提供**任务分布边界**（什么任务应该被纳入训练数据）
- 接收第 3 层反馈的**数据分布缺口**（哪些任务类型数据不足）

**Hermes 场景映射**：Kanban 任务板作为"环境"，根据 worker 执行表现动态调整任务优先级和类型分布

---

### 第 3 层：分布进化（Distribution Evolution）

**来源框架**：CoEvolve（AMAP-ML / 高德地图）

**核心思想**：Agent 失败信号 → 任务合成 → 数据分布更新。通过失败驱动的数据合成，让训练数据分布持续向 Agent 的能力边界推进。

**进化界面**：数据分布（细粒度）

**输入**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `failure_signals` | List[FailureSignal] | 失败信号（任务 ID + 失败类型 + 上下文） |
| `current_distribution` | Distribution | 当前训练数据分布统计 |
| `task_synthesizer` | Synthesizer | 任务合成器 |

**输出**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `updated_distribution` | Distribution | 更新后的数据分布 |
| `synthesized_tasks` | List[Task] | 新生成的合成任务 |
| `distribution_shift` | Dict | 分布变化记录 |

**进化机制**：
1. **失败信号捕获** — 从 Agent 执行轨迹中提取失败模式（什么任务类型、什么步骤、什么错误）
2. **任务合成** — 基于失败模式生成新的训练样本（失败案例 + 正确解法）
3. **分布更新** — 将新样本注入训练数据，调整各类任务的比例
4. **遗忘机制** — 定期移除已被 Agent 熟练掌握的样本，保持数据新鲜度

**与上下层关系**：
- 向上接收第 4 层的**任务边界约束**（合成任务不能超出环境定义的范围）
- 向下向第 2 层提供**训练数据分布先验**（哪些轨迹模式更常见/更重要）
- 接收第 2 层反馈的**轨迹质量信号**（哪些数据样本产生了高质量轨迹）

**Hermes 场景映射**：Hindsight 记忆库作为"数据分布"，根据任务执行结果动态调整记忆权重和聚类分布

---

### 第 2 层：轨迹进化（Trajectory Evolution）

**来源框架**：SE-Agent（QuantaAlpha）

**核心思想**：跨轨迹信息交换。多个推理轨迹之间不是孤立的，通过三大算子实现知识共享和策略进化。

**进化界面**：推理轨迹

**输入**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `trajectory_pool` | List[Trajectory] | 轨迹池（成功 + 失败） |
| `task_context` | Context | 当前任务上下文 |
| `failure_pattern_db` | FailurePatternDB | 失败模式库 |

**输出**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `refined_trajectory` | Trajectory | 精炼后的最优轨迹 |
| `evolution_log` | List[EvolutionStep] | 进化过程日志 |
| `reduction_stats` | Dict | 压缩统计 |

**进化机制**（三大算子闭环）：

```
┌─────────────┐    ┌──────────────┐    ┌──────────────┐
│  Revision   │───▶│ Recombination│───▶│  Refinement  │
│  (修正)     │    │  (重组)      │    │  (精炼)      │
│             │    │              │    │              │
│ 失败驱动    │    │ 跨轨迹合成   │    │ 风险感知     │
│ 策略生成    │    │ 1+1>2        │    │ 轨迹压缩     │
└─────────────┘    └──────────────┘    └──────────────┘
       ▲                                      │
       │              多轮迭代                 │
       └──────────────────────────────────────┘
```

**与上下层关系**：
- 向上接收第 3 层的**数据分布先验**（哪些轨迹模式更值得保留）
- 向下向第 1 层提供**轨迹质量信号**（用于 RL 奖励函数）
- 接收第 1 层反馈的**模型参数更新**（模型能力提升后轨迹质量基线提高）

**Hermes 场景映射**：Kanban 中同一任务的多个 worker 执行轨迹 → 通过三大算子合成最优执行路径 → 作为该任务类型的最佳实践模板

---

### 第 1 层：策略进化（Policy Evolution）

**来源框架**：RL / GRPO（通用强化学习框架）

**核心思想**：基于轨迹质量信号优化模型参数。这是最底层的进化机制，直接改变 Agent 的"大脑"。

**进化界面**：模型参数

**输入**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `trajectory_rewards` | List[float] | 轨迹质量奖励信号 |
| `policy_model` | LLM | 当前策略模型 |
| `optimizer` | Optimizer | 优化器配置 |

**输出**：
| 参数 | 类型 | 说明 |
|------|------|------|
| `updated_model` | LLM | 更新后的模型权重 |
| `policy_shift` | Dict | 策略变化记录 |
| `convergence_metrics` | Dict | 收敛指标 |

**进化机制**：
1. **奖励信号聚合** — 从第 2 层收集轨迹质量评分（成功率、效率、质量）
2. **策略梯度更新** — 使用 PPO/GRPO 等方法更新模型参数
3. **价值函数对齐** — 确保价值函数能准确预测轨迹质量
4. **稳定性控制** — 限制单次更新幅度，防止策略崩塌

**与上层关系**：
- 接收第 2 层的**轨迹质量信号**作为奖励函数输入
- 模型能力提升后，向上反馈**能力基线变化**（第 2-4 层需要相应调整阈值）

**Hermes 场景映射**：此层超出当前 Hermes 架构范围（Hermes 使用固定 LLM 模型，不涉及参数微调），但可作为未来扩展方向。

## 四、层间信号流动

```
信号流向（自底向上）：
───────────────────
第 1 层 → 第 2 层：模型能力提升 → 轨迹质量基线提高 → 进化算子阈值调整
第 2 层 → 第 3 层：轨迹质量信号 → 数据样本价值评估 → 分布权重更新
第 3 层 → 第 4 层：数据分布缺口 → 任务类型需求 → 环境任务生成方向

信号流向（自顶向下）：
───────────────────
第 4 层 → 第 3 层：任务边界约束 → 数据合成范围限制
第 3 层 → 第 2 层：数据分布先验 → 轨迹组件选择优先级
第 2 层 → 第 1 层：轨迹质量奖励 → 策略梯度更新信号
```

## 五、简化版实施路径

全量四层闭环实施成本高，建议分阶段推进：

### Phase A：第 2 层优先（轨迹进化）
- 实现三大算子（Revision / Recombination / Refinement）
- 在 Kanban 中验证多 worker 轨迹合成
- 目标：同一任务的多个执行轨迹能自动合成更优路径

### Phase B：第 2 层 + 第 3 层联动（轨迹 + 分布）
- 将轨迹进化结果反馈到 Hindsight 记忆分布
- 高质量轨迹自动提升相关记忆的权重
- 目标：记忆检索命中率随进化持续提高

### Phase C：第 2-4 层联动（轨迹 + 分布 + 环境）
- Kanban 任务板作为"环境"层，根据 worker 表现调整任务分配策略
- 目标：任务分配与 worker 能力动态匹配

### Phase D：全量四层（含策略进化）
- 需要 LLM 微调基础设施支持
- 超出当前 Hermes 架构范围，作为远期规划

## 六、关键设计决策

| 决策点 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| 层间耦合度 | 紧耦合 vs 松耦合 | 松耦合 | 各层可独立启用/降级，降低系统复杂度 |
| 进化周期 | 实时 vs 批处理 | 批处理 | 轨迹进化需要多轨迹数据，批处理更合理 |
| 失败信号来源 | 显式 vs 隐式 | 显式 + 隐式 | 显式（工具调用失败）+ 隐式（结果质量评分） |
| 轨迹存储 | 全量 vs 压缩 | 压缩存储 | 80% 体积缩减，降低存储成本 |
| 进化触发 | 自动 vs 手动 | 自动触发 + 手动干预 | 自动为主，关键节点人工审核 |

## 七、待验证问题

1. **四层信号流动的延迟问题** — 上层进化结果传递到下层需要多长时间？是否需要缓存层？
2. **失败模式库的规模控制** — 随着进化进行，失败模式库会持续增长，如何设置上限和遗忘机制？
3. **轨迹重组的冲突检测精度** — 不同轨迹的步骤组合可能产生隐性冲突，如何高效检测？
4. **四层闭环的收敛性证明** — 是否存在进化震荡或发散的风险？需要什么样的稳定性约束？
5. **Hermes 架构的适配成本** — 第 1 层（策略进化）需要 LLM 微调，当前 Hermes 不支持，如何设计降级方案？
