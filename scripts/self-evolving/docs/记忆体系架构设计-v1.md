## 一、核心问题

当前 Hindsight 所有记忆平铺在一个 embedding 空间里，知识与经验全部混在一起，同一套语义检索逻辑处理。

这导致：
- 知识（客观事实）和经验（做过的事+结果）不分，知识没有层级结构

## 二、记忆分域与术语定义

### 术语

| 层级 | 术语 | 说明 |
|------|------|------|
| 第一层 | **分域** | 知识、经验两大区 |
| 第二层 | **领域** | 半导体、软件工程、办公管理… |
| 第三层 | **科目** | 二叉树节点，逐层二分，叶子节点为知识点 |

### 分域

| 分域 | 定义 | 存储方式 | 检索策略 | 实现状态 |
|------|------|---------|---------|:------:|
| **知识** | 客观事实、方法论、答案、步骤 | 结构化树（PG parent_id）+ 图边 | 逐层科目导航定位（O(log n)，不走 LLM） | 待建 |
| **经验** | 做过的事+结果（含失败） | 平铺语义（Hindsight + Hermes memory 现有架构） | 语义匹配 + entity graph + BM25（现有的 recall） | ✅ 已实现 |

> **经验分域说明**：经验通过 Hindsight 语义检索 + Hermes MEMORY.md / USER.md 管理，当前已通过知识导航插件在线运行（pre_llm_call 注入、标记排除、时态衰减）。经验天然适合平铺语义检索，不需要树状层级，暂保持现有架构不动。
>
> **教训与技能不独立成区**：教训是做错了的经验，在经验区标注一下即可；技能是怎么做的步骤，放知识树的知识点节点中。不需要独立的分域来管理。

### 2.1 当前已跑通的部分

**经验区**已通过知识导航插件 + Hindsight recall 实现：
- `<memory-context>` 注入上下文，来源标记、时间标注齐全
- pre_llm_call 排除逻辑（标记排除 + 时态衰减）已验证

**知识区**为空，是本设计接下来要建的部分。

## 三、架构：学习与使用分离

### 学习系统（新建设，离线维护）

负责知识的组织体系和关系定义。

```
领域（半导体/软件/办公）
  └── 科目（基础理论/工程实践）
        └── 科目（工艺/设计）
              └── 科目（前道/后道）
                    └── 知识点（光刻）
```

结构特点：
- **逐层二选一**（二叉树）：每层是当前最关键的区分维度，科目名就是判据
- **上层的图只在跨域关联时使用**，底层导航走树
- **注意力机制原则**：每层只看当前最相关的判据，不一次看完所有关系

关系类型定义：
- 知识区：is-a / part-of / derives-from / depends-on / analogous-to / step-of
- 经验区：led-to / better-than / worse-than / sequence-of / causes

### 使用系统（现有 Hindsight + 知识导航插件）

负责在线召回和注入，**不增加 LLM 调用次数**。两个分域的日志各自独立记录。

```
用户 query
  │
  ▼
知识树导航（纯结构化，零矩阵，零 LLM）
  │  关键词/实体匹配 → SQL parent_id 下钻 → 定位到科目
  │
  ▼
在科目内，用注意力矩阵筛选知识点
  │  Q = query embedding
  │  K = 科目下各知识点的 embedding（或收敛后的 K 向量）
  │  attention_score = softmax(Q × K^T / √d)
  │  返回 top-3 或 top-5
  │
  ├── 获取时回写 knowledge_use_log（PG 表，记录本次被同时取出的知识点 ID）
  │    知识域日志，用于 consolidation 共现检测和使用频率计算
  │
  ├── 命中 → 送往下游融合
  └── 未命中 → 反馈路径（4.3）
  │
  ▼
Hindsight recall（经验区，现有架构）
  │  语义匹配 + BM25 + entity graph
  │  经验域日志 → trace.log（知识导航插件记录注入内容、排除标记、时间）
  │
  ▼
知识导航插件融合两个分域的结果  
  │  知识域（知识点）+ 经验域（Hindsight）  
  │  合并去重 → 排除 + 排序 → 注入 LLM 上下文  
  │  去重方式：语义相似度。如果某个知识点在知识域和经验域同时出现  
  │  （知识树节点文本与 Hindsight 记忆文本的余弦相似度 > 0.95），  
  │  只保留知识域的结果（知识树的结构化精度更高），经验域去重。  
```

**关键约束**：
- 科目定位：纯 PG 查询，0 次 LLM 调用，0 次矩阵运算
- 注意力筛选：只在科目内部做，Q 纬度固定（bge-m3 1024 维），K 向量已预存
- 融合：两个域的注入结果合并后去重
- 日志分离：经验域写 trace.log（文件），知识域写 knowledge_use_log（PG 表）

### 用户日常积累命令

知识树的使用需要给用户清晰的入口。目前设计四个命令：

| 命令 | 用途 | 说明 |
|:----|:----|:------|
| `hermes knowledge add <text>` | 加一条知识点 | 直接塞入文本，LLM 提取关键点后 attention 定位到科目 |
| `hermes knowledge ingest <file>` | 从文件批量提取 | 读取文档 → Step 1 提取 → 1.5 准入 → 干跑建树报告 |
| `hermes knowledge tree --depth N` | 查看树结构 | 纯 PG 查询，可视化科目层级 |
| `hermes knowledge find <query>` | 搜知识树 | 不走 Hindsight，直接查树 |

核心只有 `add` 和 `ingest` 两个，其他是辅助。

**知识修正命令**（用户发现知识点放错/错误/重复时手动纠错）：

| 命令 | 用途 | 说明 |
|:----|:----|:------|
| `hermes knowledge move <id/name> --to <科目名>` | 移动知识点 | 从一个科目下挪到另一个，自动更新双方 K 向量 |
| `hermes knowledge edit <id/name> --text "新内容"` | 修正文本 | 知识点的描述有误时手动修正 |
| `hermes knowledge remove <id/name>` | 删除知识点 | 错误或过时的知识点，手动移除 |
| `hermes knowledge merge <id_A> <id_B>` | 合并重复 | 两个知识点内容重复，合并为一个，合并 source_ids |

这些是手动纠错入口，跟 consolidation 自动纠错互补。

### 知识树 vs Axiom Wiki

两者互补，不冲突：

| 维度 | Axiom Wiki | 知识树 |
|:----|:----------|:------|
| 内容 | 完整文章、精读笔记、审计报告 | 提炼的关键知识点（每篇 3-8 条） |
| 使用者 | **人**逐篇阅读、查阅原文 | **系统**做知识导航、recall 定位 |
| 查询时机 | 人明确说"看原文"时才去 Wiki | 每次 recall 自动走树导航 + 注意力筛选 |
| 内容格式 | Markdown 长文 | 结构化的知识点+树+图 |

**知识树建好后将接入知识导航插件**，为现有的经验域 recall 注入增加知识域的树定位 + 注意力筛选能力。两个域的检索结果由知识导航插件融合后注入 LLM 上下文。

**Hook 注册分工**（避免功能冲突）：

| 插件 | 注册的 Hook | 职责 |
|:----|:-----------|:-----|
| `knowledge-tree-plugin` | `post_llm_call`  | LLM 响应后自动提取对话中发现的知识点 → 准入 → 增量放置 |
| `knowledge-navigation`（现有） | `pre_llm_call` | 用户 query → 融合 Hindsight（经验域）+ 知识树（知识域）→ 注入 |

`knowledge-tree-plugin` 不注册 `pre_llm_call`，`knowledge-navigation` 统一处理双域融合。

### 树图双结构

二叉树提供 O(log n) 的快速导航，但分支之间天然没有关系。跨科知识需要遍历整棵树，效率低。

**解决方案**：知识存于树上唯一位置，图只存跨科链接边，不复制知识。

```
树（knowledge_tree）：              图（knowledge_graph_edges）：
  半导体                               (器件工艺) ---相关---> (PN结)
    ├── 基础理论                       (仿真工具) ---相关---> (PN结)
    │     └── 器件物理                 (基础理论) ---推导---> (工程实践)
    │           └── PN结 ← 只在这
    └── 工程实践
          └── 器件工艺
```

使用流程：

```
在"器件工艺"下工作，需要 PN 结
  → 先查这个科有没有出边（图，O(1)）
  → 有：走图边 → 直接定位 PN 结在树上的位置
  → 没有：走树遍历（兜底，正常情况下不需要）
```

**图边的来源**：consolidation 时自动发现。

```
consolidation 统计：
  "器件工艺"下的用户，有 30% 的 recall 落在"基础理论"下
  → 树记录了这个共现模式
  → 在"器件工艺"节点上建一条跨科边 → "基础理论"
```

**存储方式**：

```sql
CREATE TABLE knowledge_tree_edges (
  id SERIAL PRIMARY KEY,
  from_node_id INT REFERENCES knowledge_tree(id),
  to_node_id INT REFERENCES knowledge_tree(id),
  relation_type VARCHAR(32),   -- 'related', 'derives-from', 'prerequisite', 等
  cooccurrence_count INT DEFAULT 1,  -- 共现次数（consolidation 递增）
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(from_node_id, to_node_id, relation_type)
);
```

**与树的边界**：
- 树负责**唯一位置**：知识点必须且只能挂在一个叶子节点下
- 图负责**跨科导航**：边是稀疏的，只建在经常跨科访问的节点之间
- 知识不复制：图里只有 node_id 引用，知识原文只在树上

## 四、各分域自动搭建总体设想

### 4.1 各分域定位

| 分域 | 核心问题 | 搭建策略 | 自动化程度 |
|:----|---------|---------|:---------:|
| **知识** | 客观事实、方法论、答案、步骤，需要层级组织 | 聚类→建树（详见第五章） | 80% 自动 |
| **经验** | 已有实现，平铺语义检索，不建树 | 维持 Hindsight + Hermes memory 现有架构 | ✅ 已实现 |

### 4.2 两个分域的关系

- **经验**是原始素材来源：用户在工作过程中发现知识缺失 → 通过经验找到答案 → 答案存入知识树
- **知识**为经验提供结构化定位：经验的 recall 结果可通过知识树领域/科目标签筛选
- **教训**（失败经验）在经验区标注即可，不独立成区
- **技能**（可执行步骤）放知识树的知识点节点中，不独立成区

### 4.3 用户找不到知识时的反馈路径（越用越聪明的关键）

这是知识树区别于传统分类系统的核心机制：

```
用户搜索 A → 知识树定位 → 没有找到 A
  ↓
用户通过其他方式找到 A 的答案（问人/实验/LLM 推理）
  ↓
这个答案就是新的知识点
    ├── 提取关键点 → 放进知识树的对应科目下
    └── 同时存入经验区："用户找 A 时没找到，通过 B 方法找到了"
  ↓
下次有人找 A：
    ├── 知识树能定位到 A 的答案
    └── 经验区能 recall 出"找不到时怎么解决"
  ↓
越用越聪明，越用越全
```

**核心原则**：
- 不存在"正确使用分域"的问题——知识负责"答案是什么"，经验负责"怎么找到的"
- 两个区通过 recall 自然互动，不需要人去判断"这个应该放知识还是经验"
- 用户在使用过程中发现的每一个知识缺口，都是知识树扩建的信号

## 五、知识分域建树逻辑（详细设计）

### 5.1 核心策略

**自底向上聚类 + 自顶向下校验**，两种互补保证树的质量。

**关键纠正**：知识树的最小单元不是文档或文档切片，而是从文章中提取的关键知识点。一篇精读笔记可能产出 3-8 个关键知识点，每个知识点才是树上的节点候选。

### 5.2 知识单元说明

知识点（knowledge point）与科目是同一类概念，只是位置不同：

| 树中位置 | 名称 | 说明 |
|---------|------|------|
| 根 | 领域 | 如"半导体" |
| 中间节点 | 科目（或子科目） | 一组知识的概括名，如"基础理论" |
| 叶子 | 知识点 | 单个知识名，如"V=IR" |

**科目和知识点在逻辑上是同一类东西**——都是"知识节点"，只是粒度不同。科目是上游的集合名，知识点是下游的具体名。

### 5.3 输入来源

| 来源 | 状态 | 处理方式 |
|------|:----:|---------|
| Wiki pages（精读笔记、审计报告） | ✅ 已有 | 直接作为输入 |
| Hindsight 高置信度记忆（score > 0.7） | ✅ 已有 | 筛选后作为输入 |
| 新导入论文/书籍/技术文档 | 手动导入 | 批量塞入待处理队列 |
| Agent 在线研究发现的知识（post_llm_call 自动捕获） | 插件新增 | 符合知识准入标准 → 自动提取 → attention 定位 → 存入树

先用 Wiki 精读笔记试跑。

### 5.4 管线步骤

#### Step 1：从文章中提取关键知识点

对每篇输入的知识文章（如精读笔记），用 LLM 提取 3-8 个关键知识点。

**关键约束**：提取提示词是第一道也是最重要的准入边界。LLM 在提取阶段就区分"该进知识树的"和"该进经验区的"。

**稳定性**：提取时设置 temperature=0 避免随机波动，同一篇文章只提取一次，不会重复跑。

```
输入：一篇精读笔记（如"精读笔记：SE-Agent"）
  │
  ▼
LLM 提取
  │  提示：
  │    "从这篇文章中提取最核心的 3-8 个知识点。
  │     只提取：理论、公式、原理、方法论、标准流程。
  │     忽略：配置参数、版本号、操作记录、文件路径、个人偏好。
  │     每个知识点一句话概括，独立可理解。"
  │
  ▼
产出：N 条知识点（如"SE-Agent 三大进化算子：Revision/Recombination/Refinement"）
```

**把关在最上游做**，不推给下游规则。规则过滤（Step 1.5）和矛盾检测只是 LLM 漏掉后的二次兜底。

每个知识点是一条独立的、自包含的文本。它们才是建树的原材料。

**知识点 vs 文档切片的区别**：

| | 文档切片（RAG） | 知识点（本设计） |
|:--|:---------------|:--------------|
| 粒度 | 按 token 数硬切 | 按语义边界提取 |
| 独立性 | 依赖上下文 | 自包含，独立可理解 |
| 数量 | 一刀切、量多 | 每篇 3-8 条 |
| 用途 | 给 LLM 看原文 | 进知识树做节点 |

#### Step 1.5：知识准入（二次过滤，兜底用）

Step 1 提取出的知识点由 LLM 在提示词中做了第一道筛选。Step 1.5 是规则驱动的二次过滤，只处理 LLM 漏掉的情况。

准入判据（每条独立判断）：
  - 自包含、独立可理解（不依赖原文上下文能看懂）
  - 有明确的领域/科目归属方向
  - 不是对原文的模糊概括（"本文讨论了..." 这种丢弃）

准入逻辑走规则，不调 LLM，避免额外调用：

```python
def is_valid_knowledge_point(text):
    # 规则1：长度太短（< 10 字）→ 丢弃
    # 规则2：以"本文"、"文章"、"本研究"开头 → 丢弃（不是独立知识）
    # 规则3：包含"讨论了"、"介绍了"、"分析了" → 丢弃（模糊概括）
    # 规则4：包含具体事实或术语（正则匹配）→ 通过
```

#### Step 2→3 检查点：建树报告

Step 2 的聚类产出是整棵树的基础。先看报告，再决定是否进 Step 3 的 LLM 校验。

**建树报告指标**：

| 指标 | 含义 | 异常信号 |
|:----|:----|:--------|
| 噪声比 | 未归入任何簇的知识点占比 | > 30% 说明参数或提取有问题 |
| 簇数 | HDBSCAN 产出的总簇数 | 过少（< 3）或过多（> 50）需排查 |
| 人工确认率 | Step 3 标记"不一致"的非叶子占比 | > 20% 说明聚类质量差 |
| 平均深度 | 树的平均层级数 | > 5 说明拆太细，< 2 说明聚太粗 |
| 叶子平均知识点数 | 每个叶子下知识点数 | 1 说明拆碎了，> 5 说明还没拆够 |
| 知识类型分布 | LLM 对每条知识标记"原理/方法论"或"配置/操作" | 配置类占比 > 5% → 报警，说明 prompt 偏了 |

**知识类型分布通过 LLM 一次批量标记获得**（建树报告生成时统一跑，不是每条单独调）：

```
对所有知识点文本，一次 LLM 调用：
  "判断每条是（A）原理/方法论/标准流程 还是（B）配置参数/操作记录"
  输出：{知识点ID: "A" | "B"}
  如果 B 占比 > 5% → 提示人工检查 Step 1 的提取 prompt
```

**检查点流程**：

```
Step 2 聚类完成
  │
  ▼
生成建树报告（指标全自动，无 LLM 调用）
  ├── 指标正常 → 继续 Step 3 LLM 校验
  └── 指标异常 → 调整 prompt/参数 → 回 Step 1 重跑
      常见调整：
        - 噪声比 > 30% → 降低 min_cluster_size 或检查提取 prompt
        - 配置类 > 5%  → 强化提取 prompt 的"忽略配置"约束
        - 平均深度 > 5  → 提高 sub-clustering 终止阈值
```

**全管线自动干跑，直到满意，输出最终树**：

```
自动干跑阶段（全自动，人不用管）：
  Step 1（提取）→ 1.5（准入）→ Step 2（聚类）
    → 建树报告
    └── 指标异常 → 调整 min_cluster_size / prompt → 回 Step 1 自动重跑
    └── 指标正常 → 进入最终跑

最终跑阶段：
  Step 3（LLM 校验）→ Step 4（LLM 命名）→ Step 5（写入 PG）
    → 最终树

人只看到结果：一棵树 + 一份建树报告
如果对树不满意，手动调 prompt/参数，再干跑一次
```

干跑阶段指标异常时的自动调整策略：

```
噪声比 > 30%       → min_cluster_size -= 1（最低到 3），重跑
配置类 > 5%        → 强化提取 prompt 的"忽略配置"约束，重跑
平均深度 > 5       → sub-clustering 终止阈值 += 2，重跑
叶子平均知识点数 < 2 → min_cluster_size -= 1，重跑

调整 3 次后指标仍异常 → 停止干跑，输出诊断报告给人
```

LLM 校验（Step 3）和命名（Step 4）成本较高（每条目一次调用），放在干跑确认聚类质量达标后再跑，不浪费。

#### Step 2：自底向上聚类（找"有什么"）

输入换成了提取出的知识点，而不是原始文档嵌入：

```
输入：M 条知识点文本（来自 N 篇文章）
  │
  ▼
embedding（bge-m3，SiliconFlow API）
  │
  ▼
HDBSCAN 聚类（min_cluster_size=5, method=eom）
  │  产出：K 个簇，每个簇是一组相似知识点
  │  （簇 ≈ 候选科目）
  │
  ▼
对每个非叶子簇递归 sub-clustering
  │  继续 HDBSCAN，直到簇内知识点数 <= min_cluster_size（<= 5 条）→ 终止，标记为叶子
  │  （注意：终止条件必须 <= min_cluster_size，否则 4 条时 ≥3 继续但 HDBSCAN 跑不了）
  │
  ▼
HDBSCAN 产出：K 个簇 + 噪声点（-1 标签）
  │  噪声点去向 → 挂在父科下作为浮动知识点，不单独成科
  │  因为这些知识点只是不够成簇，不是完全无关
  │  后续 consolidation 中如果它们反复共现 → 自然成科
  │  ⚠️ 注意：浮动知识点在树导航中不可检索（无 K 向量，无定位路径），
  │     consolidation 成科后才被纳入导航。这是临时状态。
```

产出物：一棵**自动生成的树**：

```
簇A（半导体领域）
  ├── 子簇A1（基础理论 → 科目）
  │     ├── 子簇A1a（电路原理 → 子科目）
  │     │     └── "V=IR"、"基尔霍夫定律"（知识点）
  │     └── 子簇A1b（材料物理 → 子科目）
  │           └── "PN结"、"掺杂原理"
  └── 子簇A2（工程实践 → 科目）
        └── "光刻工艺"、"版图设计"
```

#### Step 3：子簇结构判断 + 校验（LLM 一次判断）

自底向上聚类产出子簇后，Step 3 先判断子簇间的结构关系，再决定是否做二分校验：

```
对每个非叶子簇，看 sub-clustering 产出的子簇结构：
  │
  ▼
LLM 判断：
  │  "根据这些知识点文本，判断子簇之间的关系：
  │    A：平行结构（各自独立，同层级，如光刻/薄膜/清洗）
  │    B：上下位关系（一些是另一些的子领域）"
  │
  ├── A（平行）→ 保留多叉结构，不做二分校验
  │     节点名为子簇的共同上一层名称（LLM 一次命名）
  │     "半导体制造" → [光刻, 薄膜沉积, 清洗检测]
  │
  └── B（上下位）→ 走二分校验
        LLM 问："如果这些子簇分两层，最合理的二分判据是什么？"
        校验二分判据是否与 sub-clustering 的子簇对齐
        ✅ 一致 → 保留二叉树
        ❌ 不一致 → 标记人工确认
```

结果：知识树**上层多叉，下层二叉**。领域→科目→子科目用多叉（自然划分），子科目→知识点及以下用二叉（逐层精确定位）。

之前的"强制二分"逻辑已废弃。

#### Step 4：节点命名（LLM 一次命名）

```
对每个非叶子节点：
  簇内的知识点列表 → LLM → "这些知识点的共同主题是什么？"
  → 产出：科目名（4-8 字，如"基础理论"、"电路原理"）

对叶子节点：
  单个知识点文本 → LLM → "这个知识点叫什么？"
  → 产出：知识点名（如"欧姆定律"、"PN结"）
```

#### Step 5：写入 PG

```sql
CREATE TABLE knowledge_tree (
  id SERIAL PRIMARY KEY,
  parent_id INT REFERENCES knowledge_tree(id),
  name VARCHAR(128),
  node_type VARCHAR(16),   -- 'domain' | 'subject' | 'knowledge_point'
  display_order INT,
  source_ids INTEGER[],     -- 叶子节点来源于哪些文章的 ID 列表（合并去重，引用 source_articles.id）
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- 知识点原文存关联表
CREATE TABLE knowledge_point_texts (
  id SERIAL PRIMARY KEY,
  tree_node_id INT REFERENCES knowledge_tree(id),
  text TEXT NOT NULL,        -- 知识点原文（LLM 提取出的一句话）
  source_id INT              -- 这条原文来自哪篇文章（当叶子为极相似小组时，每个组员来自不同文章）
);
```

所有知识节点（领域、科目、知识点）存在树表里，`parent_id` 决定层级关系。知识点原文存在关联表中，叶子节点 ID 指向它。

**增量去重**：增量插入前，用 embedding 相似度检查是否已存在语义相同的知识点。余弦相似度 > 0.95 时不插入新节点，只合并 source_ids：

```python
def dedup_before_insert(new_point_text, leaf_nodes):
    new_embed = embed(new_point_text)
    for existing in leaf_nodes:
        if cosine_similarity(new_embed, existing.embedding) > 0.95:
            # 语义一致，不创建新节点，追加来源
            merge_source_ids(existing.id, source_article_id)
            return existing.id
    # 无重复，创建新节点
    return create_node(new_point_text, new_embed)
```

批量建树时（Step 2）HDBSCAN 聚类天然归并相似知识点，此去重针对增量场景。两个场景用同一套逻辑——批量走聚类，增量走 embedding 校验。

**知识矛盾检测**：增量插入时，检查新知识点与同科下已有知识点是否存在语义矛盾。矛盾判定不靠 LLM——用 embedding 相似度 + 关键词反向匹配：

```python
def detect_conflict(new_point_text, sibling_points):
    # 语义相似但关键词对立 → 可能矛盾
    conflict_keywords = ["不", "不是", "不能", "无效", "不再", "相反"]
    for existing in sibling_points:
        sim = cosine_similarity(embed(new_point_text), existing.embedding)
        if sim > 0.8:  # 语义足够接近
            has_negation = any(kw in new_point_text for kw in conflict_keywords)
            existing_negation = any(kw in existing.text for kw in conflict_keywords)
            if has_negation != existing_negation:  # 一个有否定词一个没有
                mark_for_human_review(new_point_text, existing.text)
                return
```

**矛盾检测只提示、不阻止插入**。但关键词否定匹配（"不"、"不是"、"不能"）误报率较高——"不推荐"含"不"但并非矛盾，"没有"也不是否定。因此矛盾检测的结果只做标记暂缓，不立即提示人。等几天后 consolidation 扫到共现数据时，**用使用共现判断比关键词靠谱**——如果两个知识点从未在同一个 attention 中被一起提取，它们大概率不相关，标记自然清除；如果反复同时出现但语义对立，才需要人工确认。

**配置类/版本类知识不进知识树**：会随时间过时的配置参数、版本号、临时工作区路径等，直接进入经验区平铺存储，不进知识树的知识点体系。知识树只存放原理、方法论、标准流程等持久知识。

## 六、注意力机制与知识定位

### 6.1 Transformer 注意力机制的原理

Transformer 的注意力（Attention）不是简单的"两个向量像不像"，而是三层分离的计算框架：

```
每个 token → 三个不同投影：
  Query  (Q)  = "我在找什么信息"（我对什么东西感兴趣）
  Key    (K)  = "我有什么信息可以给"（我的内容索引是什么）
  Value  (V)  = "我该贡献什么内容"（实际要传递的信息）

Attention Score = softmax( Q × K^T / √d )   ← 相关度打分
Output          = Score × V                  ← 按相关度加权聚合
```

核心区别在于：**相似性不等于相关性**。

一个经典例子：句子 "The cat sat on the mat because **it** was comfortable" 中的 "it" 要找到 "mat"。
- 余弦相似度：问 "it 和 mat 像不像？" → 两个代词/名词，embedding 不相似，分数低
- 注意力（QKV）：Q 问 "我在找一个能坐上去的东西" → K_mat 回答 "我是那个东西" → 分数高

**Q 和 K 是不同的投影**，各自关注不同的特征——Q 关注"需求"（要找什么类型的知识），K 关注"供给"（有什么类型的知识可给）。这是注意力机制和传统相似度计算的本质差异。

### 6.2 应用到知识树定位

在建树管线完成后，增量放置新知识点时的定位问题是：**一个新的知识点，如何找到它在树里的正确位置？**

传统方法（当前 RAG 的做法）：

```
新知识点 embedding → 和所有候选父节点算余弦相似度 → 选最高的
```

问题是：余弦相似度衡量的是"语义上像不像"，而不是"该不该放在这里"。

**注意力方法：**

```
新知识点 → 投影为 Q （"我是什么类型的知识？"）
每个候选父节点 → 投影为 K（"我的子节点应该是什么类型？"）

Attention Score = softmax( Q_new × K_parent^T )

得分最高的父节点 = 最适合的位置
```

举例说明区别：

| 新知识点 | 候选父节点 | 余弦相似度 | 注意力（Q·K） |
|---------|-----------|:---------:|:------------:|
| "FinFET 栅极结构" | "基础理论" | 0.72（相关但偏理论） | 0.28（Q说"我是具体实现"→不匹配） |
| "FinFET 栅极结构" | "工程实践→器件工艺" | 0.68（也相关） | 0.72（Q说"我是具体实现"→匹配） |

余弦相似度认为两者都"像"，注意力可以区分"该不该放这里"。

关键差异总结：

| 维度 | 余弦相似度 | 注意力（Q·K） |
|------|:---------:|:------------:|
| 角色 | 双方平等 | Q（需求）≠ K（供给） |
| 语境 | 独立打分 | softmax 强制竞争（总和=1） |
| 本质 | "我们像不像" | "我需要的是你吗" |

### 6.3 Q/K 投影向量的形成与保存：从使用中沉淀，显式存储

**Q/K 投影向量仍然需要**——没有投影就没有角色分离。这个向量不是通过离线训练一次得到的，而是**在日常使用行为中自然形成并显式保存的**。

```
每一次把知识点放到正确位置，就是一次 Q/K 关系的积累：

  人/系统将 "FinFET 栅极结构" 放入 "半导体→工程实践→器件工艺"
  
  这条操作隐含了：
    - Q 方向：这个知识点是 "具体实现类"、"器件级"、"工艺相关"
    - K 方向：这个科目的子节点通常是 "具体实现类"、"器件级"、"工艺相关"

  放得越多 → 同一科目下的知识点在 embedding 空间中围绕同一个中心收敛
  这个中心 = 该科目的 K 向量（显式保存，随放置更新）
```

**形成与保存过程**：

```
Phase 1：初始树建成 → 每个非叶子节点有一个 centroid embedding（所有子节点 embedding 的平均向量）
  │ 此时 K = centroid，Q = 新知识点的原始 embedding（未分离）
  │ → 定位效果等同于余弦相似度
  │ 该 centroid 存入 PG 表（knowledge_tree.k_vector 字段）
  │
Phase 2：每次增量放置 → 记录 (新知识点 embedding, 目标科目 ID)
  │ 同科目下的知识点 embedding 不断累加平均
  │ → 科目的 K 向量逐步从"原始 centroid"收敛为该科目特有的"子节点需求方向"
  │
Phase 3：当某科目的知识点足够多（比如 > 20 条）→ K 向量稳定
  │ 新知识点 Q 与各科目 K 的 dot product 差异显著
  │ → 定位精准，不再需要 LLM 校验
  │
持续：用的越多 → K 向量越稳定 → 定位越准 → 使用效率越高
```

**Q 向量（新知识点）的获取方式**：新知识点本身有 embedding（bge-m3），投影前直接用 embedding 作为 Q，与各候选父节点的 K 向量做 dot product + softmax。

**冷启动期回退**：在科目子节点数 < 20 条时，K 向量尚未收敛，注意力定位精度接近余弦相似度。此阶段自动回退到余弦相似度定位，等子节点数达标后切换注意力定位。初始树刚建成时所有科目都处于冷启动期，随使用积累逐步切换。

**中间段纠偏**：21-59 条之间注意力精度逐步提升，但定位不准时可能连续放错。此阶段不需要额外纠偏机制——consolidation 的共现检测会自然处理：如果 attention 放错位置，被放错的知识点会长期不与同科其他节点共现，consolidation 会标记可疑并重新归类。注意力定位不准 → 共现模式反常 → consolidation 纠正，形成闭环。

**K 向量（科目）的存储方式**：加字段到 knowledge_tree 表中：

```sql
ALTER TABLE knowledge_tree ADD COLUMN k_vector VECTOR(1024);   -- 科目的 K 投影向量
ALTER TABLE knowledge_tree ADD COLUMN placement_count INT DEFAULT 0;  -- 放置次数（冷却期计数）
ALTER TABLE knowledge_tree ADD COLUMN k_updated_at TIMESTAMPTZ;       -- K 向量最后更新时间
```

**更新策略**：每次知识点放入某科目下，更新该科目的 K 向量：

```python
# 增量更新 K 向量（指数移动平均，避免单次放置扰动过大）
alpha = min(1.0 / placement_count, 0.1)  # 前 10 次快速收敛，之后缓慢调整
new_k = (1 - alpha) * old_k + alpha * new_point_embedding
```

**关键区别**：

| 方式 | 做法 | 问题 |
|:----|:----|:-----|
| 🚫 **离线训练 Wq/Wk 矩阵** | 标注大量"知识点→正确位置"对，训练全连接层 | 没有标注数据，人工成本无限高 |
| 🚫 **纯规则/LLM标签替代** | 用 LLM 生成标签代替投影 | LLM 单次判断不可靠，标签不一致，无积累 |
| 🚫 **纯隐式** | 只通过 embedding 分布让 Q/K 方向自然浮现 | 每次重新算，看不到积累了什么 |
| ✅ **从使用中沉淀 + 显式保存 K 向量** | 使用行为自然积累，K 向量显式存入 PG | 不增加额外成本，越用越准，可检视 |

### 6.4 与 Transformer 注意力机制的对照

| Transformer 中的概念 | 本设计对应 |
|:-------------------|:----------|
| Token embedding（原始嵌入） | 知识点 embedding（bge-m3） |
| Wq / Wk 可训练投影矩阵 | **每科局部 embedding**（TaxoGen 启示，详见 6.5） |
| Q 和 K 的 dot product + softmax | Q_new 与各候选 K_parent 的 dot product + softmax → 选出最佳位置 |
| Multi-head attention（多头关注不同关系） | 不同关系类型（is-a / part-of / derives-from）对应不同投影头 |
| Cross-attention（Q 来自不同序列） | Q（新知识点）来自增量输入，K（候选父节点）来自已有树 |
| Self-attention（同类互相关注） | 同科目内知识点之间寻找关联和交叉引用 |
| Scaling factor（/√d） | 必要时对 embedding 维度做归一化，避免高分饱和 |
| 上下文窗口 | 每一层只关注同层候选人（O(log n)），不需要看整棵树 |

### 6.5 Q 没有投影的问题：TaxoGen 的启示

#### 问题

当前设计中，Q 就是新知识点的原始 bge-m3 embedding，没有经过任何投影。这意味着 Q 的判别能力受限于全局 embedding 的粒度——在粗层级（领域层）够用，在细层级（子科目层）失效。

**例子**：一个知识点 "FinFET 栅极结构" 和 "MOSFET 工作原理" 在全局 embedding 空间中距离很近（都是晶体管相关），但它们应该在树上的不同位置（一个属于"器件工艺"，一个属于"基础理论"）。全局 embedding 区分不了这种差异。

#### TaxoGen（KDD 2018）的解决方案

**TaxoGen**（UIUC Jiawei Han 组，2018）遇到了完全一样的问题：全局 Skip-Gram embedding 在粗粒度分类好用，到子科目层就糊在一起了。

他们的解法——**Local Embedding Module**：

```
TaxoGen 的做法：

  全局 embedding（整库训练）→ 只负责最上层粗分
  ↓
  到每个子科目时，不直接用全局 embedding，
  而是基于该科目下的文档集合，重新训练一个"局部 embedding"空间
  ↓
  在这个局部空间里：
    - 同科目的术语更紧凑（因为训练语料过滤了不相关上下文）
    - 不同子科的术语更分散（因为局部上下文差异被放大）
  ↓
  递归：子科再用自己的局部 embedding 细分孙子科
```

效果对比：

| 查询 | 全局 embedding 返回 | 局部 embedding 返回 |
|------|------------------|------------------|
| "pose_estimation" | single_camera, camera_pose_estimation, monocular, dof | visual_servoing, uncalibrated（更具体、更准确） |
| "information_extraction" | text_mining, named_entity_recognition, NLP | ie, extracting_information_from, question_answering（更聚焦） |

#### 映射到我们的设计

**关键认识：Q 的投影不一定要一个统一的全局 Wq 矩阵。**

TaxoGen 也没学 Wq——它用"局部语料重新训练 embedding"实现了投影效果。对应到我们：

```
我们的原始方案（旧）：
  Q = 原始 bge-m3 embedding（全局）
  K = 该科子节点平均（也是全局空间中的平均值）
  → Q 和 K 在同一个全局空间里"贴在一起"，没有分离

TaxoGen 启示的方案（新）：
  下钻到每个科目时：
    Q_local = Q 在该科局部空间中的投影
           = 用该科子节点的 embedding 分布对 Q 做一次校正
    K_local = 该科子节点局部平均（同科知识点的 embedding 质心）
  → Q_local 和 K_local 在该科的局部空间中分离度更大
```

**实现方式**（不需要训练，不需要大量标注）：

```python
# 每个科目维护一个"局部偏移向量"
# offset = centroid(该科所有子节点 embedding) - centroid(该科所有兄弟节点 embedding)
# 这个偏移向量自动捕捉了"这个科目跟兄弟科目比，独特在什么方向"

def local_q(global_embedding, subject_offset):
    """在科目局部空间中的 Q 投影"""
    return global_embedding + subject_offset * 0.3  # 偏移系数可调

# 或者更简单的做法：
# 直接在该科的兄弟范围内做对比 normalization
def attention_local(q_embed, candidate_k_list):
    """在该科兄弟范围内做 softmax，相当于局部注意力"""
    scores = [dot(q_embed, k) for k in candidate_k_list]
    return softmax(scores / sqrt(dim))  # 标准 attention 公式
```

#### 对设计的影响

| 维度 | 改动前 | 改动后 |
|:----|:-----|:------|
| Q 来源 | 全局 bge-m3 embedding（无投影） | 全局 embedding + 科室局部偏移校正 |
| 定位精度 | 粗层级可用，细层级模糊 | 每层都有自己的"局部视角"，细粒度仍可区分 |
| 存储需求 | 额外存储 | 每个科目多存一个 offset 向量（1×1024 dim） |
| 冷启动 | 初始树建成即可用 | offset 需要有子节点后才能计算（几个就够了） |
| 与 K 向量的关系 | K 单独收敛，Q 不变 | Q 和 K 在每科的局部空间中自然分离 |

## 七、知识纠错回路（Consolidation）

### 7.1 问题

知识点放错位置会污染该科目的 K 向量，错误的知识点 embedding 被平均进去后，后续同类知识点会继续放错。没有纠错机制，树的质量随使用量增长反而下降。

### 7.2 核心思路

借鉴 Hindsight consolidation 的定期审查逻辑，但不扫全量——**只 review 活跃的科目**，用注意力评分决定优先 review 哪个。

### 7.3 纠错共现的数据源

纠错依赖共现模式——需要知道"知识点 A 平时跟谁一起被召回"。这个数据源来自知识树自身的**使用日志表**。回写发生在 attention 筛选获取知识点时（top-N 取出后立即写），不是注入融合后。

**来源文章登记表**（知识树输入的引用记录）：

```sql
CREATE TABLE source_articles (
  id SERIAL PRIMARY KEY,
  wiki_path TEXT,               -- Wiki 页面路径（如 "analyses/self-evolving-agents/精读笔记-SE-Agent"）
  title TEXT,
  source_type VARCHAR(16),      -- 'wiki_note' | 'paper' | 'doc'
  extracted_at TIMESTAMPTZ      -- 知识点提取时间
);
```

每次提取知识点时，先登记文章，取 ID 后赋值给 `knowledge_point_texts.source_id` 和 `knowledge_tree.source_ids`。

**使用日志表**（记录每次注意力筛选的原始共现）：

```sql
CREATE TABLE knowledge_use_log (
  id SERIAL PRIMARY KEY,
  session_id VARCHAR(64),
  node_ids INT[],               -- 本次 attention 选出的所有知识点 ID
  query TEXT,                    -- 触发 recall 的原始查询（可选）
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**判断逻辑**：

```
同一次 attention 中一起被提取的知识点 → 天然属于同一科目
  因为注意力机制一次关注的内容就是语义上最相关的一组知识

同一科目下，长期不跟同科其他知识点同时被提取的知识点 → 可疑
  可能放错了位置，consolidation 时尝试重新归类
```

使用日志表结构：

```sql
CREATE TABLE knowledge_use_log (
  id SERIAL PRIMARY KEY,
  session_id VARCHAR(64),
  node_ids INT[],               -- 本次注入的所有知识节点 ID
  query TEXT,                    -- 触发 recall 的原始查询（可选）
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**使用频率计算（带时间衰减）**：

```python
def subject_usage_score(subject_id, days_back=30):
    """计算科目在近期内的活跃度，越近权重越高"""
    logs = query_use_log(subject_id, days_back)
    score = 0
    for log in logs:
        days_ago = (now - log.created_at).days
        weight = exp(-0.1 * days_ago)  # 指数衰减，10天衰减约63%
        score += weight
    return score
```

衰减因子 `λ = 0.1`：10 天前的使用权重 ≈ e⁻¹ ≈ 0.37，30 天前 ≈ e⁻³ ≈ 0.05。近期使用主导，旧使用快速衰减。

**位置对不对的判断链**：

```
使用日志表（使用共现 + 时间衰减）
  │
  ▼
consolidation 聚合
  │  科目 A 的知识点被同时提取的共现率
  │  同科共现高 → 位置正确
  │  跨科共现高 → 建图边（不是挪知识）
  │  同科共现低（长期单独出现，不跟同科其他节点一起被提取）→ 标记可疑，重新归类
  │
  ▼
跨科共现高 → 建图边（不是挪知识，也不是合并科目）
  图边足够解决跨科访问问题，不需要把两个科目强行合并
  只有两个科长期共现率极高（>80%）且各自知识点数都很少时，才提示人工考虑合并

### 7.4 Consolidation 流程

```
Step 1：计算各科目的 Consolidation Score（注意力评分）

  score = w1 * placement_delta + w2 * k_vector_change + w3 * days_since_review
          + w4 * recall_count_decayed

  - placement_delta：上次 review 后放了多少新知识点
  - k_vector_change：K 向量相对上次 review 的偏移量（embedding 变化量）
  - days_since_review：距上次 review 的天数
  - recall_count_decayed：近期使用频率（指数衰减，λ=0.1，30 天窗口）

  ⚫ 活跃科目 → score 高 → 优先 review
  ⚫ 安静科目（长时间无新放置）→ score 趋近 0 → 跳过
  ⚫ 这就是注意力机制——资源分配给活跃的知识，不扫全量
  │
  ▼
Step 2：按 score 排序，只 review 前 N 个活跃科目
  │
  ▼
Step 3：对活跃科目执行归属检查
  │  检查该科目下每个知识点是否真的属于这里
  │  
  │  判据方式：**实践共现**，而非数学阈值
  │  
  │  方法①（主）：检查知识点在使用中的共现模式
  │    - 在 recall 中，该知识点是否总跟同科的其他知识点一起被召回？
  │    - 在同一个任务会话中，该知识点是否常跟对应的同科知识一起被引用？
  │    - 如果一个知识点跟异科知识点的共现率 > 跟同科的共现率 → 可能放错了
  │
  │  方法②（辅）：embedding 距离
  │    - 如果知识点距离同科中心很远且距离兄弟科中心很近 → 提示人工检查
  │    - 但这不直接判决，只是提示信号
  │
  ▼
Step 4：对"疑似放错"的知识点，在兄弟科目里尝试 re‑placement
  │  用注意力评分（Q_local × K_sibling）找到最匹配的兄弟科目
  │  移动知识点 → 更新双方的 K 向量
  │  错误方：(1 - alpha) × old_k + alpha × (移除的知识点)
  │  正确方：(1 - alpha) × old_k + alpha × (新增的知识点)
```

### 7.5 与 Attention 的对应

| Attention 概念 | Consolidation 对应 |
|:---|:---|
| Q（当前需要关注什么） | 各科目的活动度（placement_delta + k_vector_change） |
| K（谁值得关注） | 高频更新科目产生高 score |
| softmax | 按 score 排序，优先 review 前 N 个 |
| 不关注低分区域 | 安静科目跳过，不跑 consolidation |

### 7.6 "置信度"不是算出来的，是用出来的

**核心认识**：不需要一个数学上的"置信度分数"。

位置对不对，不是靠 dot product 阈值判定的。而是在日常使用中自然验证的——这个思路本身就是一个注意力机制：

```
几个知识点总是反复一起被用到 → 它们天然属于同一个或相邻科目
  ↓
没有证据证明它们"放错了" → 默认是对的，不需要管
  ↓
真正的纠错触发点：
  用户在一个科目工作时，发现需要的知识点在其他科目里
  → 这时才需要判断：
     ① 这个知识点放错了，需要挪到当前科目下
     ② 知识点没放错，应该建一个跨科链接（图关系）
  ↓
核心原则：在没确定错之前，不要管
```

关键区别：

| 方式 | 问题 |
|:----|:-----|
| **数学阈值**（dot product < 0.7 = 疑似放错） | 阈值是拍脑袋的，跟实际使用无关 |
| **共现模式**（使用日志表聚合） | 由真实 recall 行为驱动，自然收敛到正确位置 |

这才是真正的 **Data Flywheel**——置信度不是算出来的，是**用出来的**。位置对不对，让使用模式说话。

### 7.7 关键约束

1. **单科目独立事务**：一次只 review 一个科目，跑错了只影响一个科目
2. **注意力驱动**：不扫全量，只 review 活跃科目
3. **不修改 Hindsight**：consolidation 逻辑独立跑在知识树上，跟 Hindsight daemon 互不干扰
4. **纠回路的出现前提**：需要先有初始树、有足够的放置行为积累出 K 向量差异后，consolidation 才有意义。在此之前纠错靠 Step 3 的 LLM 校验兜底

### 7.8 树结构演化（拆分与合并）

树不能一成不变。随着知识量增长，一个科膨胀到上百个知识点时，天然需要拆成更细的子科。

**拆分条件**：consolidation 发现某科目知识点数 > N（如 > 50 条）

```
Step 5：对知识点 > N 的科目跑 sub-clustering（跟 Step 2 一样的 HDBSCAN）
  │
  ▼
产出：K 个自然子簇
  │
  ├── K == 1（聚不成分散的子簇）→ 知识点分布均匀，不做调整
  │
  └── K >= 2（知识点自然分成几堆）
        │
        ▼
        在树里拆子科：
        原科 "器件工艺"（80 条）
          ├── 新子科 "光刻工艺"（子簇，35 条）
          └── 新子科 "封装测试"（子簇，45 条）
        │
        ▼
        更新 K 向量：
          新子科的 K = 各自子簇的 centroid
          父科的 K = 两个子科 K 的平均
        │
        ▼
        更新 parent_id：把知识点从父科移到新子科下
```

**合并条件**：consolidation 长期统计发现两个相邻科目共现率极高（>80%），且各自知识点数都很少

```
两个科 "CMP 工艺"（5 条）和 "平坦化技术"（3 条）
  │
  ▼
共现率 > 80%（几乎每次查一个都同时查另一个）
  │
  ▼
考虑顺序：先建图边 → 如果图边无法满足跨科访问需求 → 提示人工确认合并
  建图边是更低成本、可逆的方案，合并不可逆
```

**实现要点**：
- 拆分用已有的 HDBSCAN + embedding，没有新组件
- 合并走人工确认（避免误合并），系统只给提示
- 拆分后父科的 K 向量自动退化为两个子科 K 的平均，不影响上层注意力定位
- 建树（Step 2）和演化（Step 5）用同一套 sub-clustering 代码

**不做全量重建**：知识树增量维护，不触发全量 re-cluster。即使混进了少量错误知识点，只要这些知识点从未被使用，它们不参与 attention 计算、不影响 K 向量收敛、不参与共现统计，对活跃知识没有任何影响。**永远只做有用的事**——只对经常被使用的活跃科目做增量纠错和结构演化，推动注意力驱动。

## 九、未解决的问题（待验证假设）

| 假设 | 风险 |
|------|------|
| 分层树比平铺图检索更高效 | 如果领域边界模糊，二选一判据可能选错，导致路径错误 |

## 十、关于"学习和使用分开"的核心理由

- **学习**是建树、整理关系、定义领域分类 → 离线、人/脚本主动做 → 允许慢、允许试错
- **使用**是走树定位、快速下钻、召回 → 在线、低延迟 → 必须稳定、不依赖 LLM

不侵入 Hindsight 核心（不修改 hermes-agent 源码），新系统独立于 Hermes 和 Hindsight 之外，通过结构化数据接口对接。
